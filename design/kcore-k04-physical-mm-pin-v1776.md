# K04 v1776: real PDP-6 physical MM pin/refusal/recovery

Date: 2026-11-21. **PASS**: actual MM pin accounting, post-VM owner
quarantine, deferred unpin, successful real MM free and PID reuse.
The fixture is disposable and never enters production KCORE.

## Fixture construction

Start with an isolated copy of the clean, complete production v1773
PDP-6 DSK image under `$TMPDIR/daimos-k04-v1776-realpin`.
Modify **only** its generated `kcore-asm/proc_pdp6.s`, then reassemble
`proc_pdp6.dobj` with native DAS and relink/repackage the complete
boot image. The scratch-only modification is in `proc_uarea_release`:

* For slot 5 only, on its first u-area release, call real `mm_pin`
  with the u-area base from the process descriptor. Preserve the
  pinned base and a release-attempt count in three scratch BSS words.
* On subsequent attempts, check that the descriptor still owns the
  identical base; keep it pinned through nine attempts, allowing
  the unmodified `mm_free` to report `MM_ERR_BUSY` (-5).
* On the tenth attempt, call real `mm_unpin`, then call the normal
  `mm_free` with the original base, owner and type. Mark completion
  and clear the fixture base. Other slots use the original code path.

The fixture contains no fake error return, no direct mutation of MM
extent metadata and no foreign-stack release. The ordinary idle
reaper and MM provider execute. Its scratch state is not a kernel
change. Source generated by a versioned Python fixture in `$TMPDIR`;
the unmodified DAIMOS source tree and external testkit were untouched.

The full production-style 256K PDP-6 image build passed. The linked
scratch map has `k04_pin_base_v1776` at octal 025034,
`k04_pin_calls_v1776` at 025035, `k04_pin_done_v1776` at 025036,
and `__kcore_low_end` at 025167. These are **fixture-only** costs,
not production RAM growth. Fresh media passed read-only D6FS CLEAN
seq=1 before boot.

## Physical run

Real Open SIMH PDP-6 booted DAIMON V0.5 with 256K core, D6FS,
INIT and ROOT/DSH on CTY. CTY ran foreground `TRUE` and did not
return while its child PID 5 retained a pinned u-area. A separate
DCS0 ROOT login issued `PS` during the refusal interval:

    PID PPID S WORDS TD RETRY PVM DETAIL ERR COMM
    5   2    2 262143 2 512   0   6      0   USER

This shows a retained teardown owner with a 512-tick retry delay.
During the run, SIMH monitor read-only `examine 25034-25036`
observed the fixture's real pin base and increasing release count:

    25034: 000000054377
    25035: 000000000005
    25036: 000000000000

Later the count reached octal 006, 007 and 011 (nine attempts),
with the same base and incomplete flag. The CTY foreground `TRUE`
then returned to the shell prompt after the tenth attempt. DCS
`PS` showed PID 5 reused by the PS command, with TD/RETRY/PVM/
DETAIL/ERR all zero. Final read-only SIMH examination:

    25034: 000000000000   ; pinned base cleared
    25035: 000000000012   ; ten release attempts
    25036: 777777777777   ; real unpin completed

Guest `HALT` stopped at octal PC 022527, followed by SIMH `exit`.
Final read-only `d6fsck -n 4` selected superblock 742 seq=3 CLEAN,
179196 blocks and 360 FCBs. The original v1773 baseline image
was not modified.

## Scope and remaining acceptance

This is a **physical pin** test in the sense that `mm_pin` and
`mm_unpin` modify the real MM extent pin accounting, and `mm_free`
is the real provider. It is not a synthetic `kret_neg5` substitution.
The test directly demonstrates owner preservation under refusal,
repeated deferred retries, eventual real release, parent WAIT
completion and PID reuse. It does not independently read the MM
extent's pin field or count individual provider calls; the fixture
counter records entry to the u-area release routine.

The first trial's simulator console became inaccessible and its
disposable media was discarded. A subsequent trial halted in the
critical-device-lost path, and that disposable disk was also
discarded. The final accepted trial started with freshly rebuilt
CLEAN media and ended with CLEAN media. Neither aborted trial is
used as acceptance evidence.

K04 remains **OPEN** for independent multi-owner retries, clock
wrap, FILE provider refusal, session HUP, and other owner stages.
