# VFS provider 26-slot bounds and optional DTFS personalities (v21)

## Scope

The VFS target/root, D6FS reader, DTFS media, and TSFS shape/extent arrays
are already one contiguous MM-owned KINIT slab. Native FILE records and PURE
backing already support 26 mounts. The remaining explicit four-slot checks
were in the D6FS MRES service dispatch and DTFS SPACE service.

Both now check zero-based slot against the resident `vfs_mount_limit`, before
accessing the MM table; zero mount IDs and IDs greater than the published
limit fail. They do not assume a four-word array, and no additional permanent
storage is allocated. The VFS policy packs 26 readonly flags plus two five-bit
exclusive storage-owner tokens in **one 36-bit word** (v17).

## Optional TENEX and ITS personality

The normally disabled `DTFS_ENABLE_FOREIGN` branch used four mutable
`MOVEI` instructions and `XCT` to recover one mount's native/TENEX/ITS
personality. That approach is incompatible with 26 mounts, doubles the
metadata representation, and stores writable code where data already exists.

The v21 branch removes its complete four-word instruction table and its
self-modifying patch logic. `dtfs_patch_media` writes the same MM-backed
unit/owner/personality word as before. `dtfs_personality` looks up that word,
checks the zero-based mount slot against `vfs_mount_limit`, and extracts
the two personality flags (`010` for TENEX, `020` for ITS, zero for native).
An invalid mount cannot index memory beyond the allocated slab. This path
is cold relative to real DECtape transfers; the direct table lookup is
appropriately simple. Production DTFS still compiles with TENEX and ITS
disabled; enabling either personality remains separate feature validation.

Two unlinked helper prototypes (`vfs_mount_access_v5` and
`vfs_parent_mount_v6`) now validate 1..26 capacities instead of 1..16,
matching their already-dynamic table address calculations. No KCORE code is
linked from these prototypes.

## Tests and memory

The exact D6FS dispatch, DTFS SPACE, and foreign DTFS personality leaves run
in native PDP-6 validation at mounts 10 and 26, including rejection of
mount 27; the existing 26th-slot readonly/swap/logstore policy regression
passes. The full optional-foreign assembly branch assembles independently.
The production native-only disk and tape permanent-size gates pass; the
diagnostic disk-root simulator reaches ROOT login/ECHO with the documented
diagnostic-only DSH size override.

Permanent limits are unchanged from v20: disk single/multi ends `037355` /
`037416`, tape single last `036537` (octal). No new per-process or permanent
words. The strict 32K KCORE end is still `024142` octal, exceeding the
`020000` gate by 2146 decimal words. KINIT disk/tape image ends
`073042` / `074001`, with 1502/1023 words left after the bootstrap stack.
No shell boot is needed for these layout measurements.

## Remaining activation prerequisite

**Production still publishes four mounts.** KINIT currently passes the
literal `VFS_NMOUNT` (4) to `vfs_mount_slab_v4_prepare`, and the resident
`vfs_mount_limit` is initialized to four. A standalone planner,
`vfs_mount_capacity_v1`, accepts a validated controller/root-set inventory
but is **not yet called** by KINIT. KINIT does not currently possess
an authoritative unit inventory in that format. Publish the final capacity
only after deriving it from validated boot controller counts and root member
masks; preserve the bound of 26 and test mount/no-mount paths on all enabled
providers. Do not raise the static limit or infer 26 attached transports.

This v21 milestone finishes the remaining explicit provider-local bound
conversions, not complete boot-configurable mount activation.
