## Kernel completion and optimization (moved from DAIMOS/TODO.MD)

### Final kernel shrink/correctness run

#### Boot-selected memory representations and algorithm audit

INVESTIGATE WHETHER KINIT SHOULD SELECT MEMORY REPRESENTATIONS, CAPACITIES,
OR ALGORITHMS BASED ON DISCOVERED CORE, THE ACTUAL FREE-MEMORY BUDGET AFTER
ESSENTIAL DEVICE/KERNEL ALLOCATIONS, AND MEASURED WORKLOADS.  IN PARTICULAR,
TWO MACHINES WITH EQUAL INSTALLED RAM MAY NEED DIFFERENT CACHE BUDGETS.

- FIRST, AUDIT MM'S FIXED 32-ENTRY, TWO-WORD-PER-EXTENT TABLE: EVALUATE A
  RUNTIME-SIZED DESCRIPTOR ARRAY AND ITS MINIMUM CAPACITY FOR NESTED
  MAKE/KCC/KCPP PROCESSES.  COMPARE LINEAR SORTED LOOKUP AGAINST OPTIONAL
  INDEXES ONLY FOR LARGER CONFIGURATIONS.  DO NOT ADD TREES WITHOUT EVIDENCE.
- SECOND, AUDIT D6FS/DTFS/TSFS BLOCK CACHE CAPACITIES AND REPLACEMENT COST.
  INCLUDE DECTAPE SEEK LATENCY AND REAL NATIVE-COMPILATION I/O; COMPARE SMALL
  LINEAR CACHES WITH LARGER CACHES AND OPTIONAL LOOKUP INDEXES.
- THIRD, PROFILE DIRECTORY LOOKUP UNDER NATIVE MAKE/KCC BUILDS.  COMPARE
  LINEAR DIRECTORY SCANS WITH A SMALL ENTRY CACHE OR OPTIONAL HASH INDEX;
  REUSE EXISTING D6FS NAME HASHING WHERE APPROPRIATE.
- FOURTH, COMPLETE MM-AUTHORITATIVE PACKED DESCRIPTOR OWNERSHIP AND COMPARE
  DENSE DIRECT-INDEX LAYOUT STORAGE WITH BOUNDED SPARSE SLOT/LAYOUT ENTRIES.
  SHARE VALIDATION, TEARDOWN, AND PUBLICATION CODE; KINIT SHOULD SELECT THE
  REPRESENTATION/CAPACITY IF MEASUREMENTS JUSTIFY SUPPORTING BOTH.  DO NOT
  ENABLE PACKED EVICTION OR INTEGRATE THE DEFERRED PRODUCTION CODEC HERE.
- FIFTH, PROFILE SCHEDULER RUN-QUEUE SCANS AT HIGH PROCESS COUNTS BEFORE
  CONSIDERING OPTIONAL PRIORITY INDEXES; PRESERVE THE INTRUSIVE SMALL-SYSTEM
  QUEUE AND AVOID A BRANCHY POLICY DISPATCH ON EVERY SCHEDULER HOT PATH.
- SIXTH, EVALUATE PIPE BUFFER CAPACITY SEPARATELY FROM DEFERRED VARIABLE
  6/7/8/9/18/36-BIT PIPE WORD WIDTHS.  PREFER A SMALL DEFAULT AND BOUNDED
  CAPACITY CHOICES WHEN THROUGHPUT/WORKING-SET MEASUREMENTS JUSTIFY THEM.
- RETAIN THE EXISTING BOOT-SELECTED PROCESS SLOT COUNT; INVESTIGATE OPTIONAL
  AUXILIARY INDEXES ONLY AFTER REAL LARGE-CORE CONCURRENCY MEASUREMENTS.

FOR EACH CANDIDATE, MEASURE POST-P10FOLD PERMANENT KCORE TEXT/DATA/BSS,
BOOT-TIME DYNAMIC WORDS AND MM DESCRIPTORS, PEAK PROCESS RAM, WORST-CASE
EXECUTION COST, AND MAXIMUM CONCURRENCY.  COMPARE TOTAL RAM COST, NOT ONLY
THE SIZE OF ONE TABLE.  PREFER SHARED CODE WITH BOOT-SELECTED DATA LAYOUT
OVER TWO PERMANENTLY LINKED ALGORITHMS; OPTIONAL LARGER-MEMORY CODE MUST NOT
MAKE THE 32K KCORE GROW.  ONLY IMPLEMENT VARIANTS WITH MEASURED NET VALUE.
ALL TESTS BELONG IN DAIMOS-TESTKIT.  DO NOT CHANGE THE ACTIVE CONFIGURATION
UNTIL 32K BOOT/LOGIN/PROCESS-PRESSURE ACCEPTANCE PASSES.

BEFORE SWITCHING FULLY TO USERLAND:

- MAKE ONE RESIDENT-SIZE OPTIMIZATION SWEEP UNTIL THE PERMANENT KERNEL IS BELOW
  THE HARD `040000` ADDRESS LIMIT.
- FIX ANY COMPILER, ASSEMBLER, KERNEL, FILESYSTEM, OR DEVICE CORRECTNESS ERROR
  FOUND DURING THAT SWEEP AT ITS SOURCE; DO NOT WORK AROUND IT IN USERSPACE.
- ADD OR UPDATE A REGRESSION TEST FOR EVERY REPRODUCIBLE CORRECTNESS FIX.
- RUN THE RELEVANT KERNEL/BOOT/LOGIN ACCEPTANCE TESTS AFTER THE FINAL SHRINK
  CHANGES.  AFTER THIS RUN, NORMAL DEVELOPMENT MOVES TO USERLAND.


## KCORE-targeted fold/superoptimization backlog

### P10FOLD and P10SUPER

#### Cross-domain folding decision gate

- RERUN THE P10FOLD READ-ONLY CROSS-DOMAIN CENSUS AFTER THE CURRENT DAIMOS
  OPTIMIZATION RUN COMPLETES.  USE THE FINAL KCORE HANDWRITTEN OBJECTS AS `-a`
  ANCHORS, PASS THE FINAL KCORE FOLD PLAN WITH `-x`, AND MAINTAIN AN EXPLICIT
  COLD-FUNCTION `-C` ALLOWLIST FOR ONE-JRST DONORS.  HOT OR UNKNOWN FUNCTIONS
  MUST REMAIN UNLISTED.
- IMPLEMENT EXECUTABLE EXTERNAL-ANCHOR DLINK FOLDING ONLY IF THE FINAL
  NON-OVERLAPPING ZERO-COST PLUS COLD ONE-JRST SAVING REMAINS MATERIAL,
  APPROXIMATELY MORE THAN 20 PERMANENT WORDS.  CROSS-DOMAIN FOLDING MAY NOT
  GROW KCORE OR ADD TARGET-SIDE METADATA.

#### Deferred until self-hosting

- DO NOT MODIFY KCC-GENERATED ASSEMBLER DIRECTLY.  AFTER SELF-HOSTING, USE
  P10SUPER AS AN ORACLE FOR GENERAL KCC CODE-GENERATOR CANONICALIZATION,
  INCLUDING CROSSJUMP/COMMON-TAIL CHOICES, SCRATCH-AC ALLOCATION, INSTRUCTION
  ORDERING, BRANCH ORIENTATION, AND EQUIVALENT INSTRUCTION FORMS.
- DEFER FULL SEMANTIC SUPEROPTIMIZATION, SMT-BASED EQUIVALENCE PROOFS, LARGE
  EXHAUSTIVE SEARCHES, AND OPTIONAL MULTICORE/CUDA SEARCH ACCELERATION UNTIL
  THE SIMPLE HANDWRITTEN-ASSEMBLER WORK IS EXHAUSTED.
- DEFER THE NATIVE LOW-MEMORY P10FOLD IMPLEMENTATION UNTIL THE SELF-HOSTING
  TOOLCHAIN PATH NEEDS IT.  THE NATIVE DESIGN SHOULD FAVOR COMPACT DESCRIPTORS,
  STREAMING/MULTI-PASS SEARCH, AND EXACT RELOCATION-AWARE VERIFICATION OVER
  HOST-STYLE RAM CONSUMPTION.
