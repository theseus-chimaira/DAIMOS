# DAIMOS SIZE OPTIMIZATION FINDINGS

DATE: 2026-10-01

THIS FILE IS A LIVING CATALOG OF SIZE-OPTIMIZATION FINDINGS, CANDIDATES, AND
DELIBERATE NON-CANDIDATES FOR THE DAIMOS KERNEL.  IT IS NOT AN IMPLEMENTATION
LOG.  COMPLETED CHANGES BELONG IN GIT HISTORY; OPEN REQUIRED WORK BELONGS IN
TODO.MD; ARCHITECTURE STATE BELONGS IN PROJECT-STATE.MD.

THE PRIMARY GOAL IS TO REDUCE PERMANENT KCORE+MRES FOOTPRINT WITHOUT ADDING
TARGET-SIDE METADATA, HIDDEN RAM COST, OR EXECUTION OVERHEAD THAT OUTWEIGHS THE
SAVING.  SOURCE-LEVEL SIMILARITY ALONE IS NOT A REASON TO SHARE CODE.  A
CONSOLIDATION IS USEFUL ONLY WHEN THE SEMANTICS ARE ACTUALLY COMMON AND THE
FINAL LINKED IMAGE IS MEASURABLY SMALLER.

## 1. CURRENT CONSOLIDATIONS ALREADY IN PLACE

THE LARGE OBVIOUS COMMON MECHANISMS ARE ALREADY SHARED:

- FS_COPY_WORDS, FS_MOVE_WORDS, AND FS_ZERO_WORDS.
- VFS NAME VALIDATION, COMPARISON, AND MATERIALIZATION HELPERS.
- COMMON FILESYSTEM PROVIDER VECTOR DISPATCH.
- SERIALIZATION OF SLEEPING FILESYSTEM PROVIDERS.
- PROC_WAIT_EVENT / PROC_WAKEUP_EVENT.
- COMMON FILESYSTEM MEMORY-RECLAIM CLASSES.
- BCACHE FOR CLEAN FILESYSTEM BLOCK COPIES.
- BACKSTORE FOR PROCESS SWAP AND MEMFS BACKING.
- FILESYSTEM BACKING DESCRIPTORS.
- COMMON STORAGE REQUEST DESCRIPTOR INITIALIZATION.
- SHARED S6REC VALIDATION.
- SHARED D6LZ DECODE ENGINE.
- COMMON CONSTANT RETURN TAILS.
- SHARED STORAGE PI ROUTING.

THERE IS NO LONGER AN OBVIOUS LARGE GENERIC SUBSYSTEM WAITING TO BE MERGED.
THE REMAINING OPPORTUNITIES ARE SMALLER AND MUST BE MEASURED CAREFULLY.

## 2. HIGHEST-VALUE CONSOLIDATION CANDIDATES

### 2.1 STORAGE MAP + READ/WRITE DISPATCH

SEVERAL STORAGE LAYERS IMPLEMENT THE SAME GENERAL CONTROL SHAPE:

    READ ENTRY  -> SET READ SELECTOR  -> COMMON BODY
    WRITE ENTRY -> SET WRITE SELECTOR -> COMMON BODY
    COMMON BODY -> VALIDATE/MAP -> SELECT BACKEND -> DISPATCH

THIS PATTERN APPEARS IN:

- STORAGE/BLOCKSET_DISPATCH.S
- STORAGE/BADMAP_DISPATCH.S
- STORAGE/FS_BACKING.S
- DRIVERS/DSK270.S
- DRIVERS/DRM236.S
- FS/FS_MRES.S RAW BACKSTORE-TAIL ROUTING

THE TWO COMMON CONCEPTS ARE:

    LOGICAL -> PHYSICAL MAPPING
    PHYSICAL BLOCK -> DEVICE I/O

THESE CONCEPTS ARE ALREADY PARTLY SEPARATED BY FS_BACKING, BLOCKSET, AND
BADMAP, BUT EACH LAYER STILL CARRIES SOME LOCAL READ/WRITE SELECTION AND
DISPATCH CODE.

INVESTIGATE WHETHER ONE VERY SMALL COMMON TAIL CAN REPLACE ENOUGH DUPLICATED
INSTRUCTIONS TO REDUCE THE FINAL LINKED IMAGE.  DO NOT INTRODUCE A GENERAL
CALLBACK FRAME OR MULTI-LAYER INDIRECT CALL CHAIN UNLESS MEASUREMENT SHOWS A
NET SAVING.  ON PDP-6, THREE LOCAL BRANCHES CAN EASILY BE SMALLER AND FASTER
THAN A GENERIC ABSTRACTION.

EXPECTED VALUE: MODERATE; POSSIBLY SEVERAL TO A FEW DOZEN WORDS.

### 2.2 DSK270 / DRM236 PHYSICAL-I/O GATEWAY

DSK270.S AND DRM236.S SHARE ALMOST THE SAME VALIDATION/READ-WRITE ENTRY SHAPE:

    SET READ/WRITE SELECTOR
    VALIDATE BUFFER
    VALIDATE UNIT 0..3
    VALIDATE RH18 ADDRESS
    CHECK DEVICE-SPECIFIC LIMIT
    CONVERT TO DEVICE ADDRESS
    DISPATCH THROUGH PATCHED READ/WRITE JUMP

THE COMMON VALIDATION SEQUENCE IS NEARLY IDENTICAL.  THE PRINCIPAL DIFFERENCE
IS ADDRESS TRANSLATION:

- DSK: LINEAR SECTOR -> CYLINDER/SECTOR ADDRESS.
- DRM: BLOCK -> TYPE-236 GROUP ADDRESS.

INVESTIGATE A TINY COMMON VALIDATION TAIL ONLY IF IT MEASURES SMALLER THAN THE
CURRENT FALL-THROUGH CODE.  DO NOT FACTOR IT MERELY FOR SOURCE CLEANLINESS.

EXPECTED VALUE: SMALL.

### 2.3 COMMON STORAGE REQUEST COMPLETION / WAIT LIFECYCLE

STORAGE_REQUEST_INIT ALREADY UNIFIES THE THREE-WORD ASYNCHRONOUS REQUEST
DESCRIPTOR USED BY RESIDENT STORAGE DRIVERS.  DSK AND DRM STILL HAVE SIMILAR
HIGH-LEVEL REQUEST LIFECYCLES:

    BUILD REQUEST
    CLAIM OR QUEUE
    START HARDWARE
    SLEEP ON COMPLETION
    PI COMPLETES REQUEST
    WAKE WAITER
    RETURN STATUS

THE SCHEDULERS THEMSELVES MUST REMAIN DIFFERENT:

- DSK USES A BOUNDED PER-UNIT ELEVATOR.
- DRM USES EXACTLY ONE PENDING REQUEST.
- TAPE HAS DIFFERENT MECHANICAL STATE AND MUST REMAIN SPECIALIZED.

THE COMPLETION/WAIT MECHANICS MAY STILL SUPPORT ONE SMALL SHARED HELPER NEXT
TO STORAGE_REQUEST_INIT.  MEASURE BEFORE RETAINING SUCH A HELPER.

EXPECTED VALUE: SMALL TO MODERATE.

## 3. KCORE-LEVEL REPRESENTATION CANDIDATES

### 3.1 VFS FIXED-SIZE TABLE OPERATIONS

VFS REPEATEDLY OPERATES ON SMALL FIXED TABLES, ESPECIALLY THE FOUR MOUNT
SLOTS, PROVIDER FIELDS, BUILT-IN MONITORFS NAMES, AND PACKED VNODE FIELDS.
LOOKUP MOUNT CROSSING AND PARENT MOUNT CROSSING ARE RELATED OPERATIONS OVER THE
SAME TABLES.

DO NOT AUTOMATICALLY ADD CALLABLE HELPERS.  FIRST CHECK WHETHER TABLE LAYOUT OR
PACKING CAN LET MULTIPLE OPERATIONS USE FEWER INSTRUCTIONS.  REPRESENTATION
CHANGES THAT SHRINK SEVERAL KCORE PATHS ARE MORE ATTRACTIVE THAN ADDING A
GENERIC ITERATOR.

EXPECTED VALUE: SMALL, BUT EVERY WORD IS PERMANENT KCORE.

### 3.2 FILE DESCRIPTOR TABLE SCANS

FILE_RUNTIME.S REPEATEDLY WALKS THE 16-ENTRY, TWO-WORD FILE DESCRIPTOR TABLE:

- FILE_DUP
- FILE_LOCK CONFLICT SCAN
- FILE_LOCK UPDATE SCAN
- FILE_UNLOCK_MOUNT
- FILE_CLOSE_ALL

THE LOOPS SHARE THE SAME TABLE STRIDE AND COUNT BUT HAVE DIFFERENT BODIES.
AVOID A CALLBACK-BASED GENERIC ITERATOR.  INSTEAD, CHECK WHETHER THE PACKED
DESCRIPTOR REPRESENTATION CAN BE ADJUSTED SO SEVERAL OF THESE OPERATIONS NEED
FEWER TESTS OR MASKING INSTRUCTIONS.

EXPECTED VALUE: SMALL TO MODERATE IF ONE REPRESENTATION CHANGE HELPS SEVERAL
ROUTINES.

### 3.3 PROCESS TABLE ADDRESS CALCULATION

MULTIPLE PROCESS/VM PATHS COMPUTE:

    PROC = PROC_TABLE + SLOT * 3

WITH A SHORT SHIFT/ADD SEQUENCE.  A CALLABLE HELPER IS NOT ATTRACTIVE BECAUSE
THE CURRENT INLINE CALCULATION IS ONLY A FEW INSTRUCTIONS.  A PERMANENT
CURRENT-PROCESS POINTER WOULD COST STATE AND PUBLICATION COMPLEXITY.

CURRENT ASSESSMENT: KEEP INLINE UNLESS A DIFFERENT PROCESS-DESCRIPTOR LAYOUT
MAKES THE CALCULATION CHEAPER AS A SIDE EFFECT.

## 4. DUPLICATION THAT SHOULD PROBABLY REMAIN SPECIALIZED

### 4.1 FILESYSTEM DIRECTORY SCANS

MEMFS, D6FS, DTFS, AND TSFS ALL VALIDATE NAMES, SCAN ENTRIES, COMPARE NAMES,
AND RETURN VNODES, BUT THEIR STORAGE SEMANTICS DIFFER SUBSTANTIALLY:

- MEMFS SCANS COMPACT LIVE NODES.
- D6FS USES HASHED ON-MEDIA DIRECTORY ENTRIES.
- DTFS SUPPORTS NATIVE AND MULTIPLE FOREIGN-MEDIA PERSONALITIES.
- TSFS SCANS IMMUTABLE TABLE RECORDS.

THE CORRECT COMMON BOUNDARY IS ALREADY THE VFS NAME HELPERS.  A GENERIC
DIRECTORY-SCAN CALLBACK LAYER WOULD LIKELY COST MORE CODE AND EXECUTION TIME.

### 4.2 ALLOCATION BITMAPS

BACKSTORE, D6FS, AND DTFS ALL CONTAIN ALLOCATION-LIKE BITMAP OR MAP LOGIC, BUT
THEIR SEMANTICS ARE DIFFERENT:

- BACKSTORE: DIRECT RAM BITMAP, FIRST-FIT RUN ALLOCATION, RESERVE POLICY.
- D6FS: ON-MEDIA BITMAP PLUS SUMMARY STATE, TRANSACTIONAL UPDATE, I/O FAILURE
  HANDLING, AND FILESYSTEM EXTENTS.
- DTFS: DECTAPE-SPECIFIC OWNER/ALLOCATION MAP SEMANTICS.

DO NOT BUILD A GENERIC ALLOCATOR FOR THESE.  THE CURRENT SHARING OF BACKSTORE
BETWEEN PROCESS SWAP AND MEMFS IS THE CORRECT CONSOLIDATION.

### 4.3 DEVICE BUSY FLAGS / LOCKING

PTR, PTP, CR, CP, BCACHE, FILESYSTEM PROVIDERS, DSK, AND DRM ALL HAVE SOME FORM
OF BUSY/OWNERSHIP STATE, BUT THEY DO NOT SHARE ONE LOCKING SEMANTIC.

POLLING CHARACTER/MEDIA DEVICES OWN THEIR HARDWARE SYNCHRONOUSLY FOR A SHORT
CALL.  FILESYSTEM PROVIDERS MAY SLEEP THROUGH DISK I/O AND THEREFORE NEED THE
PROC_WAIT_EVENT SERIALIZATION PATH.  STORAGE REQUEST QUEUES HAVE THEIR OWN
COMPLETION EVENTS.

DO NOT INTRODUCE A GENERIC KERNEL MUTEX FOR THESE CASES.

### 4.4 PTR/PTP AND CR/CP SYMMETRY

THE READER/PUNCH PAIRS HAVE NOTICEABLE IDENTICAL REGISTER SAVE/RESTORE
SEQUENCES, BUT THEIR HARDWARE STATE MACHINES AND PACK/UNPACK DIRECTIONS DIFFER.
THE EXACT SOURCE DUPLICATION IS MOSTLY CALLING-CONVENTION BOILERPLATE.

DO NOT FACTOR SAVE/RESTORE INTO RUNTIME HELPERS UNLESS MEASURED CODE SIZE
PROVES A NET SAVING.

### 4.5 STORAGE SCHEDULERS

DO NOT UNIFY DSK, DRM, AND TAPE SCHEDULERS.  THEIR POLICIES ARE FUNDAMENTALLY
DIFFERENT AND THE CURRENT SMALL SPECIALIZED IMPLEMENTATIONS ARE INTENTIONAL.

## 5. SAVE/RESTORE AND STACK-FRAME PATTERNS

P10SUPER/CLONE ANALYSIS SHOWS MANY REPEATED ASSEMBLER FRAME SEQUENCES, SUCH AS
PUSH/POP OF AC10..AC15 AND FIXED BLT-BASED FRAME COPIES.

THESE SHOULD NOT BECOME TARGET-SIDE RUNTIME HELPERS BY DEFAULT.  THE BETTER
LONG-TERM TARGET IS THE TOOLCHAIN:

- EXPRESS COMMON SOURCE PATTERNS WITH DAS MACROS WHERE THAT IMPROVES SOURCE
  MAINTAINABILITY WITHOUT CHANGING MACHINE CODE.
- LET KCC/DAS OPTIMIZATION REMOVE UNNECESSARY SAVES WHEN REGISTER LIVENESS
  PROVES THEM DEAD.
- TREAT ANY INCORRECT SAVE/RESTORE GENERATION AS A COMPILER/ASSEMBLER BUG AND
  FIX IT AT THE TOOLCHAIN SOURCE.

## 6. P10SUPER ASSESSMENT

P10SUPER IS NOT A GENERAL GLOBAL SUPEROPTIMIZER, BUT FOR ITS CURRENT INTENDED
ROLE ON HANDWRITTEN DAIMOS ASSEMBLER ITS SEARCH SPACE IS EFFECTIVELY
EXHAUSTED.

THE CURRENT TOOL ALREADY HANDLES:

- CAI/CAM/JUMP/AOJ/SOJ CONTROL SHAPES.
- SKIP/AOS/SOS AND TR/TL CONDITIONAL FAMILIES.
- COMPLEMENTARY BRANCH CONDITIONS WITH EXCHANGED SUCCESSORS.
- CONSERVATIVE STRAIGHT-LINE SCHEDULING.
- DIRECT AC/MEMORY ALIAS MODELING FOR EFFECTIVE ADDRESSES 0..17.
- ZERO-FORM CANONICALIZATION.
- REGION-LOCAL AC RENAMING.
- PROVEN ONE-WORD PEEPHOLE SHORTENINGS.
- RELOCATION-AWARE SEMANTIC COMPARISON.
- GLOBAL NON-CONFLICTING CANDIDATE SELECTION.

THE LAST COMPLETE HANDWRITTEN-KCORE PASS FOUND 14 INDEPENDENT ONE-WORD
SHORTENINGS.  THEY HAVE ALREADY BEEN APPLIED.  THE FOLLOW-UP PASS FOUND TEN
LEGAL SCHEDULING MATCHES, BUT NONE HAD POSITIVE PAIR-PROVEN FOLD SAVING, SO
GLOBAL SELECTION CORRECTLY RETAINED NONE.  NO PEEPHOLE, ZERO-FORM, OR AC-RENAME
CANDIDATE REMAINS IN THE CURRENT HANDWRITTEN KCORE PASS.

THEREFORE DO NOT EXPAND P10SUPER MERELY TO CHASE THE CURRENT FINAL KERNEL
SHRINK.  THE PROBABLE RETURN IS LOW COMPARED WITH DIRECT KERNEL
CONSOLIDATION/REPRESENTATION WORK.

### 6.1 FUTURE HIGH-VALUE P10SUPER WORK

P10SUPER BECOMES MORE VALUABLE AGAIN WHEN KCC-GENERATED CODE AND SELF-HOSTING
ARE THE TARGET.  FUTURE EXTENSIONS WORTH CONSIDERING INCLUDE:

1. USE P10SUPER AS AN ORACLE FOR KCC CODE-GENERATOR IMPROVEMENTS:
   SCRATCH-AC SELECTION, BRANCH ORIENTATION, CROSSJUMP/COMMON-TAIL CHOICES,
   INSTRUCTION ORDERING, AND EQUIVALENT INSTRUCTION FORMS.
2. EXTEND SEMANTIC INSTRUCTION COVERAGE WHERE CURRENT UNKNOWN/BARRIER
   CLASSIFICATION BLOCKS OTHERWISE LEGAL REORDERING.
3. ADD BOUNDED LONGER PEEPHOLE SEARCHES FOR SHORTER EQUIVALENT TWO-TO-FOUR
   INSTRUCTION SEQUENCES.
4. CONSIDER CAREFULLY BOUNDED CROSS-BASIC-BLOCK TAIL MERGING AND BRANCH
   RESTRUCTURING.
5. CONSIDER COST-AWARE DIRECT SIZE REDUCTIONS THAT DO NOT DEPEND ON EXPOSING
   AN EXACT P10FOLD MATCH.

FULL SMT-STYLE OR EXHAUSTIVE SUPEROPTIMIZATION REMAINS DEFERRED UNTIL SIMPLE
GENERATED-CODE OPPORTUNITIES ARE EXHAUSTED.

### 6.2 P10FOLD BEFORE MORE P10SUPER

FOR THE CURRENT FINAL KERNEL SIZE RUN, THE MORE PROMISING TOOLING FOLLOW-UP IS
THE EXISTING CROSS-DOMAIN P10FOLD CENSUS, NOT EXPANDING P10SUPER.

RERUN THE CROSS-DOMAIN CENSUS AFTER THE CURRENT KERNEL OPTIMIZATION IS STABLE,
USING THE FINAL HANDWRITTEN KCORE OBJECTS AS ANCHORS AND THE FINAL KCORE FOLD
PLAN AS EXCLUSIONS.  IMPLEMENT EXECUTABLE EXTERNAL-ANCHOR FOLDING ONLY IF THE
FINAL NON-OVERLAPPING ZERO-COST PLUS EXPLICITLY COLD ONE-JRST SAVINGS REMAIN
MATERIAL, APPROXIMATELY MORE THAN 20 PERMANENT WORDS, AND ONLY IF KCORE DOES
NOT GROW AND NO TARGET-SIDE METADATA IS REQUIRED.

## 7. CURRENT PRIORITY ORDER

THE FINAL SHRINK SWEEP HAS TWO USEFUL CLASSES OF WORK.  DO NOT LET THE DEEPER
RAM/REPRESENTATION OPPORTUNITIES DISPLACE CHEAP CODE-SIZE WINS WHICH CAN BE
MEASURED AND RETAINED QUICKLY.

CHEAP OR LOW-RISK FIRST-PASS CANDIDATES:

1. STORAGE MAP/READ/WRITE TAIL CONSOLIDATION.
2. DSK/DRM REQUEST COMPLETION AND WAIT COMMONALITY.
3. VFS MOUNT-TABLE REPRESENTATION AND OPERATIONS.
4. FILE DESCRIPTOR REPRESENTATION AND REPEATED TABLE SCANS.
5. DSK/DRM PHYSICAL GATEWAY VALIDATION.
6. TOOLCHAIN SAVE/RESTORE OPTIMIZATION RATHER THAN TARGET-SIDE HELPERS.

DEEPER STRUCTURAL CANDIDATES WHICH MAY SAVE MORE RAM AND SHOULD BE MEASURED
AFTER OR ALONGSIDE THE CHEAPER PASSES:

7. REMOVE POST-MOUNT DEAD FIELDS FROM LIVE FILESYSTEM/STORAGE STATE.
8. FUSE MM FIT/FREE/FRAGMENTATION SCANS.
9. AUDIT U-AREA AND KERNEL-STACK LIFETIMES FOR SAFE OVERLAYS AND A SMALLER
   PER-PROCESS U-AREA.
10. AUDIT RESIDENT STRUCTURE FIELD LAYOUT FOR TARGET-INSTRUCTION COST.
11. FUSE OTHER RELATED SMALL-TABLE SCANS WHERE ONE PASS CAN RETURN MULTIPLE
   RESULTS WITHOUT NEW STATE.
12. FINAL CROSS-DOMAIN P10FOLD CENSUS AFTER THE SOURCE-LEVEL SHRINK IS STABLE.

AVOID GENERIC FILESYSTEM DIRECTORY SCANNERS, GENERIC BITMAP ALLOCATORS,
GENERIC DEVICE MUTEXES, AND GENERIC STORAGE SCHEDULERS UNLESS NEW MEASUREMENT
PROVES THAT THE CURRENT SPECIALIZED DESIGN IS LARGER.

## 8. FUZIX-DERIVED SIZE-OPTIMIZATION CONCEPTS

FUZIX IS USEFUL AS A SMALL-UNIX REFERENCE BECAUSE IT CONSISTENTLY OPTIMIZES
FOR FIXED SMALL TABLES, SHORT LIFETIMES, AND MINIMAL LIVE KERNEL STATE.  DAIMOS
ALREADY USES MANY OF THE SAME IDEAS MORE AGGRESSIVELY, ESPECIALLY THREE-WORD
PROCESS DESCRIPTORS, STATE-DEPENDENT FIELD REUSE, KINIT RECLAMATION, COMPACT
VNODE/FILE METADATA, SMALL LINEAR TABLES, AND SPECIALIZED DEVICE DISPATCH.

THE MOST USEFUL REMAINING FUZIX LESSON IS NOT TO COPY ITS UNIX INTERFACES, BUT
TO APPLY THREE RULES SYSTEMATICALLY:

1. KEEP ONLY STATE WHICH IS LIVE AFTER INITIALIZATION.
2. REUSE STORAGE WHEN LIFETIMES CANNOT OVERLAP.
3. MAKE ONE TABLE TRAVERSAL ANSWER EVERY QUESTION IT CAN.

### 8.1 TRIM LIVE RUNTIME STATE AFTER MOUNT/INITIALIZATION

FUZIX FREQUENTLY KEEPS ONLY THE SMALL KERNEL-REQUIRED SUBSET OF ON-MEDIA OR
USER-VISIBLE METADATA AFTER A RESOURCE HAS BEEN VALIDATED AND ATTACHED.

DAIMOS SHOULD APPLY THIS AS A GENERAL POST-KINIT/MINIT AUDIT RULE:

    IS THIS WORD STILL REQUIRED AFTER THE INVARIANT HAS BEEN ESTABLISHED?

IF NOT, IT SHOULD NOT REMAIN IN LIVE RUNTIME STATE.

D6FS IS A CONCRETE CANDIDATE.  STRUCT D6FS_READER EMBEDS STRUCT
D6FS_SUPER_INFO, INCLUDING:

- SEQUENCE
- STATE
- FS_UUID[2]
- TOTAL_BLOCKS
- ROOT_FCB
- FCB_START
- FCB_COUNT
- FREEMAP_START
- FREEMAP_BLOCKS

CURRENT SOURCE USE SHOWS THAT SEVERAL OF THESE ARE BOOT/MOUNT VALIDATION OR
HANDOFF DATA RATHER THAN ORDINARY RESIDENT I/O STATE.  FS_UUID HAS NO CURRENT
RESIDENT RUNTIME REFERENCE.  SEQUENCE, ROOT_FCB, FCB_START, AND FREEMAP
LOCATION DATA ALSO APPEAR TO BE CONSUMED DURING BOOT/MOUNT SETUP RATHER THAN
NORMAL FILE I/O.  STATE IS ALREADY REPURPOSED AS A RUNTIME CACHE TAG, WHICH IS
THE RIGHT STYLE OF LIFETIME REUSE.

DO NOT CHANGE THIS LAYOUT UNTIL EVERY ASSEMBLER/C CALLBACK OFFSET AND MOUNT
HANDOFF USE HAS BEEN AUDITED.  THE GOAL IS A SMALL RUNTIME D6FS STATE, NOT A
SECOND PARALLEL STRUCTURE WITH COPY OVERHEAD.

APPLY THE SAME AUDIT TO:

- DTFS/TSFS MOUNT STATE.
- MEMFS MOUNT/PROVIDER STATE.
- LOGSTORE STATE.
- BLOCKSET/BADMAP STATE.
- AUXSTORE BOOT/HANDOFF STATE.
- ANY KINIT/MINIT HANDOFF OBJECT WHICH SURVIVES INTO NORMAL RUNTIME.

EXPECTED VALUE: POTENTIALLY HIGH DYNAMIC-RAM SAVING, ESPECIALLY WHEN SAVED PER
MOUNT OR PER PROVIDER.  POSSIBLE SECONDARY CODE-SIZE SAVING FROM FEWER COPIES
AND OFFSET OPERATIONS.

### 8.2 U-AREA AND KERNEL-STACK LIFETIME OVERLAYS

FUZIX USES ITS PER-PROCESS UDATA AS REUSABLE SCRATCH FOR I/O, SYSCALL, AND
SWAP STATE WHEN THOSE LIFETIMES CANNOT OVERLAP.  DAIMOS ALREADY HAS THE SAME
BROAD ARCHITECTURE: A TINY RESIDENT PROCESS DESCRIPTOR PLUS A STABLE PRIVATE
U-AREA CONTAINING DESCRIPTORS, CREDENTIALS, CONTEXT, AND KERNEL STACK.

THE NEXT STEP IS TO AUDIT ACTUAL DAIMOS KERNEL-STACK LIFETIMES.  LOOK FOR
MULTIWORD FRAMES OR TEMPORARIES WHICH ARE:

- PROCESS-PRIVATE.
- LIVE ACROSS CALLS OR SLEEPS.
- MUTUALLY EXCLUSIVE WITH OTHER LARGE TEMPORARIES.
- SAFE TO PLACE IN A FIXED U-AREA SCRATCH OVERLAY.

THE GOAL IS NOT MERELY TO REMOVE A FEW PUSH INSTRUCTIONS.  THE IMPORTANT WIN
WOULD BE TO REDUCE THE REQUIRED KERNEL-STACK HIGH-WATER MARK ENOUGH TO SHRINK
PROC_UAREA_WORDS.

EVEN SMALL PER-PROCESS SAVINGS SCALE WELL.  FOR EXAMPLE, EIGHT WORDS REMOVED
FROM EACH U-AREA SAVE 192 WORDS AT 24 PROCESSES, 320 WORDS AT 40 PROCESSES,
AND 512 WORDS AT 64 PROCESSES.

ANY STATE WHICH SURVIVES PROC_WAIT_EVENT() OR ANOTHER SLEEPING EXECUTIVE
CONTINUATION MUST REMAIN STABLE AND PROCESS-PRIVATE.  DO NOT COPY FUZIX
ASSUMPTIONS WHICH RELY ON NON-OVERLAPPING I/O UNLESS DAIMOS CAN PROVE THE SAME
LIFETIME.

EXPECTED VALUE: POTENTIALLY VERY HIGH DYNAMIC-RAM SAVING, BUT REQUIRES CAREFUL
STACK-LIFETIME ANALYSIS AND STRONG REGRESSION COVERAGE.

### 8.3 FUSE MM FIT, FREE-SPACE, AND FRAGMENTATION SCANS

FUZIX'S SMALL MEMORY MANAGERS OFTEN COMPUTE SEVERAL RELATED RESULTS DURING ONE
PASS INSTEAD OF MAINTAINING EXTRA INDEXES OR RESCANNING TINY TABLES.

DAIMOS CURRENTLY HAS A DIRECT OPPORTUNITY IN MM.C:

- MM_FIND_FIT() SCANS ARENAS AND EXTENTS.
- AFTER A FAILED FIT, MM_ALLOC_ALIGNED_NORECLAIM() CALLS MM_TOTAL_FREE() TO
  DISTINGUISH MM_ERR_FRAGMENTED FROM MM_ERR_NOMEM.
- MM_COMPACT() ALSO CALLS MM_TOTAL_FREE() AND THEN MM_FIND_FIT().

A FAILED MM_FIND_FIT() HAS ALREADY VISITED THE ALLOCATION MAP NEEDED TO KNOW
TOTAL FREE CORE.  THE FIT PASS CAN THEREFORE RETURN ENOUGH INFORMATION TO
DISTINGUISH:

    FIT FOUND
    NO FIT BUT ENOUGH TOTAL FREE CORE -> FRAGMENTED
    INSUFFICIENT TOTAL FREE CORE      -> NOMEM

ON A SUCCESSFUL LOW-PLACEMENT SEARCH IT CAN STILL RETURN IMMEDIATELY.  ONLY
THE FAILURE PATH NEEDS TO ACCUMULATE COMPLETE FREE-SPACE INFORMATION.

THIS MAY ALSO ALLOW MM_TOTAL_FREE() TO DISAPPEAR FROM KCORE IF NO OTHER USER
REQUIRES IT.

EXPECTED VALUE: SMALL CODE-SIZE SAVING, FEWER EXTENT-TABLE TRAVERSALS UNDER
MEMORY PRESSURE, AND NO NEW PERSISTENT STATE.  THIS IS A PARTICULARLY STRONG
LOW-RISK CANDIDATE.

### 8.4 DATA LAYOUT SHOULD FOLLOW PDP-6 INSTRUCTION COST

FUZIX DELIBERATELY ORDERS STRUCTURE FIELDS FOR TARGET MACHINE CODE, NOT FOR C
AESTHETICS.  DAIMOS ALREADY DOES THIS FOR PROC, VNODE, FILE, MM EXTENTS, AND
SEVERAL DEVICE-STATE WORDS, BUT THE RULE SHOULD BE APPLIED TO EVERY RESIDENT
OR FREQUENTLY ACCESSED STRUCTURE.

FOR EACH STRUCTURE, ASK:

- CAN TWO HALF-WORD-SIZED VALUES SHARE ONE 36-BIT WORD?
- CAN BOOLEAN/ENUM STATE OCCUPY OTHERWISE DEAD BITS?
- ARE FIELDS WHICH ARE USUALLY LOADED TOGETHER POSITIONED TO REDUCE ADDRESS
  CALCULATION?
- CAN STATE-DEPENDENT VALUES REUSE ONE WORD?
- CAN AN EXISTING VNODE, FILE, OR PROVIDER FIELD CARRY A VALUE INSTEAD OF A
  NEW WORD?
- CAN FIELD ORDER DELETE AN INSTRUCTION FROM EVERY HOT ACCESS?

GOOD AUDIT TARGETS INCLUDE D6FS_READER, D6FS RUNTIME METADATA, FS_BACKING,
LOGSTORE, BLOCKSET, PROCESS SWAP RECORDS, AND MEMFS NODE/PROVIDER STATE.

EXPECTED VALUE: INDIVIDUAL CHANGES MAY BE SMALL, BUT THEY CAN REDUCE BOTH
PERSISTENT RAM AND REPEATED ACCESS CODE.

### 8.5 ONE SCAN SHOULD RETURN MULTIPLE RELATED FACTS

THE MM CASE ABOVE IS THE CLEAREST EXAMPLE, BUT THE SAME RULE SHOULD BE USED
WHEN REVIEWING SMALL DAIMOS TABLES.  IF A LOOP ALREADY VISITS EVERY ENTRY, IT
SHOULD COMPUTE ALL CHEAPLY RELATED RESULTS NEEDED BY THE CALLER RATHER THAN
FORCING A SECOND PASS.

POSSIBLE REVIEW TARGETS:

- FILE DESCRIPTOR SCANS.
- VFS MOUNT TABLE SCANS.
- PROCESS TABLE SELECTION/ACCOUNTING PASSES.
- MM EXTENT SCANS.
- SMALL PROVIDER OR DEVICE TABLES.

DO NOT FUSE PASSES IF DOING SO REQUIRES PERSISTENT INDEX STATE, EXTRA COMPLEX
CALLBACKS, OR MAKES THE COMMON SUCCESS PATH LONGER.  THE FUZIX LESSON IS TO
EXPLOIT INFORMATION ALREADY AVAILABLE DURING A NECESSARY LINEAR PASS.

### 8.6 KEEP TINY TABLES LINEAR

FUZIX EXPLICITLY USES LINEAR SEARCHES WHEN THE TABLE IS SMALL.  THIS SUPPORTS
THE CURRENT DAIMOS DESIGN FOR TWO-BLOCK BCACHE, FOUR MOUNT SLOTS, SMALL
PROCESS/FILE TABLES, BADMAP, AND SIMILAR STRUCTURES.

DO NOT ADD HASH TABLES, TREES, OR RESIDENT INDEXES FOR THESE CASES.  WHEN A
LINEAR PASS IS ALREADY CHEAP, PREFER RETURNING MORE USEFUL INFORMATION FROM
THAT PASS OVER MAINTAINING A SECOND DATA STRUCTURE.

### 8.7 KINIT RECLAMATION ALREADY SUPERSEDES FUZIX DISCARD SECTIONS

FUZIX CAN PLACE BOOT-ONLY CODE/DATA INTO A DISCARD AREA AND REUSE THE SAME RAM
AS BLOCK BUFFERS AFTER BOOT.  DAIMOS KINIT RECLAMATION THROUGH THE GENERAL MM
ALLOCATOR IS MORE FLEXIBLE: THE RECLAIMED WORDS MAY SERVE PROCESSES, CACHE,
MEMFS, MODULES, OR OTHER DEMAND.

DO NOT ADD A SPECIAL DISCARD-TO-CACHE PATH.  INSTEAD VERIFY THAT EVERY
BOOT-ONLY BUFFER, HANDOFF TABLE, AND SCRATCH ALLOCATION IS ACTUALLY RETURNED OR
REPURPOSED AFTER KINIT/MINIT.

### 8.8 PROCESS DESCRIPTOR SPLIT ALREADY MATCHES THE USEFUL FUZIX MODEL

FUZIX KEEPS SCHEDULER-VISIBLE STATE IN A SMALL PROCESS TABLE AND LARGER
PROCESS-PRIVATE STATE IN UDATA.  DAIMOS ALREADY TAKES THIS FURTHER WITH A
THREE-WORD PROCESS DESCRIPTOR AND STABLE U-AREA.

DO NOT MOVE MORE STATE BACK INTO STRUCT PROC.  FUTURE SAVINGS SHOULD COME FROM
REDUCING U-AREA CONTENT OR OVERLAYING STATE, NOT GROWING THE RESIDENT PROCESS
TABLE.

### 8.9 DO NOT COPY FUZIX DEVSWTCH OR GENERAL DIRTY BLOCK CACHE

FUZIX'S CLASSIC DEVICE-SWITCH TABLE WITH OPEN/CLOSE/READ/WRITE/IOCTL FUNCTION
POINTERS IS CLEAN BUT IS NOT A GOOD DAIMOS SIZE MODEL.  DAIMOS PATCHED JUMPS,
MRES PACKAGES, AND COMPACT OPERATION-SPECIFIC VECTORS ARE BETTER SUITED TO
36-BIT WORD COSTS AND OPTIONAL HARDWARE.

SIMILARLY, FUZIX'S GENERAL DIRTY BLOCK CACHE REQUIRES DEVICE/BLOCK TAGS,
DIRTY/BUSY/LRU STATE, WRITEBACK POLICY, AND SYNCHRONIZATION.  DAIMOS'S CLEAN
TWO-BLOCK BCACHE IS INTENTIONALLY MUCH SMALLER.

ONE FUZIX I/O IDEA MAY BE REVISITED ONLY AS A SPEED OPTIMIZATION: A FULL-BLOCK
OVERWRITE NEED NOT FIRST READ THE OLD BLOCK.  DO NOT ADD SPECIAL-CASE CODE FOR
THIS DURING THE SIZE SWEEP UNLESS IT ALSO REMOVES EXISTING CODE OR STATE.

### 8.10 SWAPPING THE U-AREA IS DEFERRED

SOME FUZIX MEMORY MODELS CAN SWAP PROCESS-PRIVATE UDATA AND USE TEMPORARY
KERNEL STATE DURING THE SWAP.  DAIMOS KEEPS ITS U-AREA RESIDENT SO A PROCESS
MAY SLEEP INSIDE THE EXECUTIVE WITH A STABLE KERNEL STACK AND CONTINUATION.

SWAPPING QUIESCENT U-AREAS COULD SAVE RAM, BUT WOULD REQUIRE NEW STATE
CLASSIFICATION, SERIALIZATION, RESTORE PATHS, AND SPECIAL SWAP CONTEXT.  THAT
COMPLEXITY IS NOT APPROPRIATE FOR THE CURRENT 0.9 SIZE PASS.

CURRENT ASSESSMENT: INTERESTING FUTURE IDEA, NOT AN IMPLEMENTATION CANDIDATE
NOW.

## 10. DEC MONITOR 1.4-DERIVED SIZE-OPTIMIZATION CONCEPTS

DEC PDP-6 TIMESHARING MONITOR 1.4 IS AN ESPECIALLY USEFUL REFERENCE BECAUSE
ITS DESIGN TARGETS THE SAME MACHINE FAMILY AND CORE ECONOMICS.  MANY OF ITS
GENERAL I/O ABSTRACTIONS ARE TOO LARGE FOR DAIMOS, BUT SEVERAL LOW-LEVEL
TECHNIQUES ARE DIRECTLY RELEVANT.

### 10.1 BOOT-LINK PI HANDLER CHAINS INSTEAD OF TABLE/SPAN ITERATION

MONITOR 1.4'S LINKSR ROUTINE BUILDS EACH PRIORITY-INTERRUPT SERVICE CHAIN AT
INITIALIZATION TIME BY PATCHING THE CONTINUATION OF ONE DEVICE HANDLER TO THE
NEXT.  A PI LEVEL THEREFORE EXECUTES AS A DIRECT CHAIN OF JRSTS AND ENDS AT THE
CHANNEL RETURN, WITHOUT A RESIDENT HANDLER-ADDRESS TABLE OR GENERIC ITERATOR.

DAIMOS CURRENTLY HAS:

- PDP10_PI_HANDLERS: 010 WORDS.
- PDP10_PI_LEVEL_SPAN: 007 WORDS.
- GENERIC PDP10_PI_DISPATCH / PDP10_PI_HANDLER_RETURN ITERATION.
- ONE SPAN LOAD IN EACH PI LEVEL ENTRY.

MINIT ALREADY PATCHES SINGLE-HANDLER LEVELS DIRECTLY TO THEIR HANDLER, SO THE
MONITOR IDEA IS SPECIFICALLY ATTRACTIVE FOR MULTI-HANDLER LEVELS.

INVESTIGATE GIVING EACH RESIDENT PI HANDLER ONE PATCHABLE COMMON EXIT WORD.
MINIT CAN THEN PATCH THAT EXIT EITHER TO THE NEXT HANDLER AT THE SAME LEVEL OR
TO PDP10_PI_RETURN_COMMON.  ALL INTERNAL HANDLER EXITS BRANCH TO THAT ONE
PATCHABLE TAIL.

THIS COULD REMOVE THE 15-WORD HANDLER/SPAN BSS, THE GENERIC TABLE ITERATOR,
AND THE PER-LEVEL SPAN LOADS.  A FIRST-ORDER SAVING OF APPROXIMATELY 25 OR MORE
PERMANENT WORDS IS PLAUSIBLE.

RUNTIME MODULE UNLOADING IS NOT CURRENTLY IMPLEMENTED.  IF ADDED LATER, THE
CHAIN CAN BE REBUILT WITH PI DISABLED RATHER THAN RETAINING A PERMANENT
ITERATOR FOR THAT FUTURE POSSIBILITY.

EXPECTED VALUE: VERY HIGH FOR A LOCAL KCORE REFACTOR; MEASURE EXACT LINKED
SIZE AND PI LATENCY.

### 10.2 USE BLT FOR CONTIGUOUS PROCESS AC SAVE/RESTORE

MONITOR 1.4 DELIBERATELY LAYS OUT SAVED CONTEXT SO A SINGLE BLT COPIES A
CONTIGUOUS REGISTER RANGE BETWEEN LIVE ACS AND JOB STORAGE.

DAIMOS PROC_SAVE_USER, PROC_SAVE_KERNEL, PROC_RESTORE_USER, AND
PROC_RESTORE_KERNEL CURRENTLY CONTAIN LONG SCALAR MOVE/MOVEM RUNS FOR AC0 AND
AC4..AC16.  AC1..AC3 ARE ALREADY SAVED SEPARATELY BY PI6 LOW-CORE SCRATCH.

AT MINIMUM, AC4..AC16 FORM A CONTIGUOUS SOURCE AND DESTINATION RANGE AND ARE A
DIRECT BLT CANDIDATE.  A MORE AGGRESSIVE SAVE MAY COPY A BROADER RANGE AND
THEN OVERWRITE AC1..AC3 WITH THEIR AUTHORITATIVE PI6 COPIES.

THE SAME PRINCIPLE APPLIES TO RESTORE.  EXACT PDP-6 BLT SEMANTICS, AC17
SAFETY, INTERRUPT ENTRY STATE, AND THE CONTEXT LAYOUT MUST BE VERIFIED WITH
THE FULL SWITCH/SLEEP TEST SUITE.

EXPECTED VALUE: ROUGHLY 20-30+ KCORE WORDS, WITH FEWER EXECUTED INSTRUCTIONS.

THIS IS ALSO A FUTURE P10SUPER/ASSEMBLER OPTIMIZATION PATTERN: RECOGNIZE A
PROVEN CONTIGUOUS SCALAR MOVE/MOVEM RUN AND REPLACE IT WITH BLT WHEN ALIASING
AND ENDPOINTS MAKE THE TRANSFORMATION SAFE.

### 10.3 MOVE LARGE NON-PROCESS SCRATCH OFF THE PER-PROCESS STACK

MONITOR 1.4 USES SHARED EXECUTIVE SCRATCH EXTENSIVELY BECAUSE EXECUTIVE CODE
IS NOT ARBITRARILY PREEMPTED.  THIS SUGGESTS A TARGETED DAIMOS RAM
OPTIMIZATION WITHOUT ADOPTING THE MONITOR'S ENTIRE BLOCKING MODEL.

D6LZ36_DECODE_VFS CURRENTLY RESERVES A 0100-WORD (64 DECIMAL) VFS REFILL
WINDOW ON THE CURRENT PROCESS KERNEL STACK, IN ADDITION TO SAVED ACS AND TWO
PERSISTENT LOCALS.  THE CURRENT ACCEPTANCE-WORKLOAD PROCESS-STACK WATERMARK IS
ABOUT 0307 OCTAL WORDS, SO THIS LARGE FRAME CONTRIBUTES DIRECTLY TO THE
CURRENT 0420-WORD U-AREA REQUIREMENT.

INVESTIGATE MOVING ONLY THE D6LZ INPUT WINDOW TO ONE SHARED KERNEL-DYNAMIC
BUFFER PROTECTED BY A SMALL LOCK/EVENT.  THE LOCK MUST COVER THE COMPLETE
DECODE, NOT JUST ONE VFS READ, BECAUSE THE DECODER MAY SLEEP INSIDE VFS AND A
SECOND EXEC MUST NOT OVERWRITE THE WINDOW WHILE THE FIRST CONTINUATION EXISTS.

DO NOT REUSE FS_BLOCK_WORKSPACE DIRECTLY: THE FILESYSTEM PROVIDER SERVICING
THE D6LZ REFILL MAY ITSELF NEED THAT WORKSPACE.  USE A DISTINCT SHARED D6LZ
WINDOW OR PROVE A SAFE LIFETIME RELATION FIRST.

AFTER THE CHANGE, RERUN THE FULL PROCESS-STACK WATERMARK WORKLOAD.  IF THE
HIGH-WATER FALLS BY ABOUT 64 WORDS, PROC_UAREA_WORDS MAY BE REDUCED BY A
SIMILAR AMOUNT.  AT 24 ACTIVE PROCESSES, A 64-WORD PER-PROCESS REDUCTION IS
1536 WORDS BEFORE THE COST OF ONE SHARED WINDOW AND TINY CONTROL STATE.

EXPECTED VALUE: POTENTIALLY VERY HIGH DYNAMIC-RAM SAVING FOR A MODEST LOCAL
SERIALIZATION TRADE.

### 10.4 CONTINUATION-FREE BLOCKING IS THE MAJOR LONG-TERM RAM ALTERNATIVE

MONITOR 1.4 DOES NOT PRESERVE AN ARBITRARILY DEEP EXECUTIVE CALL STACK FOR
EVERY BLOCKED JOB.  WAIT1/WSYNC MARK THE JOB WAITING, FORCE SCHEDULING, AND
LATER RECHECK/RESUME THROUGH KNOWN CONTROL POINTS.  PER-JOB MONITOR STATE IS
KEPT IN A SMALL PROTECTED JOB DATA PREFIX AND ONE SHARED CURRENT-USER SYSTEM
AREA.

THE MONITOR'S JOB DATA AREA IS 0140 OCTAL = 96 WORDS TOTAL, AND ITS EXECUTIVE
PUSHDOWN LIST IS ONLY ABOUT 016 OCTAL = 14 WORDS.  DAIMOS CURRENTLY RESERVES
0420 OCTAL = 272 WORDS PER U-AREA, INCLUDING ABOUT 0306 OCTAL WORDS OF
PROCESS-PRIVATE KERNEL STACK.

DAIMOS'S LARGER STACK IS NOT ACCIDENTAL: FILESYSTEM, STORAGE, AND OTHER
SYSCALL PATHS MAY PROC_WAIT_EVENT() DEEP IN THE EXECUTIVE AND LATER RESUME THE
EXACT SAVED CONTINUATION.  THE CURRENT WATERMARK SHOWS THE STACK IS ACTUALLY
USED; SIMPLY LOWERING PROC_UAREA_WORDS IS UNSAFE.

THE MONITOR DEMONSTRATES THE OTHER ARCHITECTURAL EXTREME: REPRESENT A BLOCKED
OPERATION AS SMALL EXPLICIT RESTART STATE, RETURN TO THE SCHEDULER, AND
REENTER/RECHECK WHEN THE RESOURCE WAKES THE JOB.

THIS COULD EVENTUALLY SHRINK DAIMOS PER-PROCESS EXECUTIVE STORAGE BY WELL OVER
100 WORDS PER PROCESS, BUT IT WOULD REQUIRE SYSTEMATIC RESTRUCTURING OF
BLOCKING PATHS AND IS NOT AN APPROPRIATE 0.9 PATCH.

CURRENT ASSESSMENT: MAJOR POST-0.9 RAM-ARCHITECTURE OPTION.  BEFORE ANY SUCH
REDESIGN, EXHAUST LOCAL SHARED-SCRATCH AND STACK-FRAME REDUCTIONS.

### 10.5 USE SLEEP BOUNDARIES TO DECIDE WHAT MUST BE PROCESS-PRIVATE

MONITOR 1.4 REINFORCES THE JOSS/FUZIX LIFETIME RULE.  WHEN REVIEWING A LARGE
DAIMOS FRAME OR SCRATCH OBJECT, CLASSIFY IT AS:

- ACTUAL PROCESS STATE WHICH MUST SURVIVE A SWITCH.
- TRANSIENT EXECUTIVE SCRATCH WHICH NEVER LIVES ACROSS A SLEEP.
- SCRATCH WHICH LIVES ACROSS A SLEEP ONLY BECAUSE THE ENCLOSING OPERATION IS
  CURRENTLY REENTRANT.

THE SECOND CLASS SHOULD PREFER ACS, SHORT STACK FRAMES, OR SHARED WORKSPACE.
THE THIRD CLASS MAY BE A GOOD SERIALIZATION CANDIDATE IF ONE SHARED BUFFER
SAVES SUBSTANTIAL PER-PROCESS RAM AND THE OPERATION IS INFREQUENT, SUCH AS
COMPRESSED EXEC DECODE.

### 10.6 SKIP-RETURN ABI FOR ASSEMBLY-ONLY INTERNAL HELPERS

MONITOR 1.4 HEAVILY USES PDP-6 SKIP RETURNS, INCLUDING SHARED CPOPJ/CPOPJ1/
CPOPJ2 TAILS.  A ROUTINE CAN SIGNAL SUCCESS OR A SMALL NUMBER OF OUTCOMES BY
ADVANCING ITS SAVED RETURN PC RATHER THAN MATERIALIZING A STATUS INTEGER IN AN
AC AND REQUIRING THE CALLER TO TEST IT.

DO NOT CHANGE C-FACING DAIMOS ABIS.  INSTEAD, AUDIT HANDWRITTEN ASSEMBLY-ONLY
HELPERS WITH MANY CALL SITES OF THE FORM:

    PUSHJ 17,HELPER
    JUMP*/CAI* RESULT,...

IF A SKIP-RETURN CONTRACT REMOVES MORE CALLER TESTS THAN IT ADDS TO THE
HELPER, IT MAY SAVE A FEW KCORE/MRES WORDS.

EXPECTED VALUE: SMALL; LOW PRIORITY AFTER PI/BLT/STACK WORK.

### 10.7 DEVICE IDENTITY SHOULD NOT REQUIRE PARALLEL RESIDENT TABLES

MONITOR 1.4 PLACES THE PHYSICAL SIXBIT DEVICE NAME IN THE DEVICE DATA BLOCK
ITSELF, SO DEVICE IDENTITY AND RUNTIME STATE SHARE ONE OBJECT.

DAIMOS CORRECTLY AVOIDS GENERAL DDBS, BUT MONITORFS CURRENTLY RESERVES ONE
FULL WORD PER DEVICE IN MFSDEV_NAMES.  MOST NAMES ARE SHORT STEM+0 FORMS SUCH
AS CTY0, CLK0, PTR0, DSK0, AND LPT0.

INVESTIGATE ONLY AS A MICRO-OPTIMIZATION WHETHER NAMES CAN BE RECONSTRUCTED
FROM A SMALL PACKED STEM TABLE PLUS EXISTING DEVICE-ID/PRESENCE INFORMATION.
DO NOT ADD A GENERAL DDB LAYER.  RETAIN THE CURRENT FULL-WORD ARRAY IF NAME
RECONSTRUCTION CODE COSTS MORE THAN THE SAVED DATA.

EXPECTED VALUE: PROBABLY ONLY A FEW WORDS.

### 10.8 VARIABLE PI AC-SAVE DEPTH IS NOT DIRECTLY TRANSFERABLE

MONITOR 1.4 GENERATES PI CHANNEL SAVE AREAS SIZED TO THE HIGHEST AC REQUIRED
BY DEVICES CONFIGURED ON THAT CHANNEL.  DAIMOS'S COMMON PI DISPATCH ABI
ITSELF REQUIRES AC1..AC3 AND AC17 ON ACTIVE LEVELS, AND THE AC17 SAVE TABLE'S
UNREACHABLE ODD SLOTS ARE ALREADY OVERLAID WITH OTHER GLOBAL STATE.

THERE IS NO OBVIOUS DIRECT DATA SAVING HERE.  THE USEFUL MONITOR TECHNIQUE IS
THE LINKED HANDLER CHAIN, NOT COPYING ITS VARIABLE SAVE-DEPTH MECHANISM.

### 10.9 MONITOR DDB AND BUFFER-RING ARCHITECTURE SHOULD NOT BE COPIED

MONITOR 1.4'S DEVICE DATA BLOCKS AND COMMON IOCONT/IOCSS LAYERS SHARE BUFFER
RING MANAGEMENT, BYTE POINTERS, ITEM COUNTS, MODE BITS, AND DEVICE DISPATCH
ACROSS MANY DEVICES.  THIS IS EFFECTIVE FOR ITS GENERAL BYTE/BUFFERED I/O
ABI, BUT THE COMMON STRUCTURES AND RING HEADERS ARE LARGE.

DAIMOS'S WORD-STREAM ABIS, WORDTOKEN8, CARD12, S6REC, CALLER-OWNED BUFFERS,
AND PATCHED OPTIONAL MRES ENTRIES ARE SMALLER FOR THE CURRENT TARGET.

DO NOT INTRODUCE GENERAL DDBS OR MONITOR-STYLE RING BUFFERS FOR SIZE REASONS.

### 10.10 1K CORE BITMAP ALLOCATION IS TOO COARSE FOR DAIMOS

MONITOR 1.4 TRACKS CORE WITH A VERY COMPACT 1-BIT-PER-1024-WORD BLOCK MAP PLUS
CORTAL AND A SEARCH POINTER.  THE METADATA IS SMALLER THAN DAIMOS'S VARIABLE
EXTENT TABLE, BUT 1024-WORD ALLOCATION GRANULARITY WOULD WASTE FAR MORE RAM
THROUGH INTERNAL FRAGMENTATION THAN IT SAVES IN METADATA.

DO NOT ADOPT THE MONITOR CORE ALLOCATOR.  THE USEFUL LESSON IS TO DERIVE OR
CACHE MULTIPLE ALLOCATION FACTS DURING ONE NECESSARY SCAN; THE ALREADY-NOTED
MM FIND-FIT/FREE/FRAGMENTATION FUSION IS THE BETTER DAIMOS APPLICATION.

### 10.11 ONCE-ONLY INITIALIZATION IS ALREADY SUPERSEDED BY KINIT

MONITOR 1.4 DELIBERATELY PLACES ONCE-ONLY INITIALIZATION CODE BEYOND THE
PERMANENT MONITOR END SO THAT MEMORY CAN LATER BELONG TO USERS.  DAIMOS KINIT
RECLAMATION IS THE MORE GENERAL VERSION AND SHOULD BE KEPT.

### 10.12 REVISED CHEAP/CURRENT PRIORITY AFTER MONITOR 1.4

THE CURRENT MEASUREMENT ORDER SHOULD NOW INCLUDE:

1. BLT PROCESS CONTEXT SAVE/RESTORE.
2. BOOT-LINK MULTI-HANDLER PI CHAINS.
3. REMOVE REDUNDANT PTR/PTP/CR/CP SOFTWARE BUSY WORDS.
4. FUSE MM FIT/FREE/FRAGMENTATION SCANS.
5. STORAGE MAP/READ/WRITE TAIL CONSOLIDATION.
6. COMMON DSK/TAPE DCT SETUP.
7. DSK/DRM COMPLETION/WAIT COMMONALITY.
8. VFS/FILE-TABLE REPRESENTATION OPTIMIZATIONS.
9. SKIP-RETURN EXPERIMENTS FOR ASSEMBLY-ONLY HELPERS.
10. MONITORFS DEVICE-NAME COMPRESSION ONLY IF MEASURED POSITIVE.

IN PARALLEL, THE HIGHEST-VALUE RAM EXPERIMENT IS MOVING THE 64-WORD D6LZ VFS
REFILL WINDOW TO ONE SERIALIZED SHARED DYNAMIC BUFFER AND THEN RERUNNING THE
FULL PROCESS-STACK WATERMARK TEST TO DETERMINE WHETHER PROC_UAREA_WORDS CAN BE
REDUCED.

## 11. ITS 138-DERIVED SIZE-OPTIMIZATION CONCEPTS

ITS 138 USES MANY OF THE SAME PDP-6 TECHNIQUES AS MONITOR 1.4, BUT PUSHES
RESTARTABLE EXECUTIVE OPERATIONS, PACKED RESOURCE STATE, AND DIRECTLY INDEXED
PER-USER STORAGE FURTHER.  ITS IS NOT A GOOD WHOLE-SYSTEM MODEL FOR DAIMOS,
BUT SEVERAL MECHANISMS SHARPEN OR EXTEND THE PREVIOUS SIZE FINDINGS.

### 11.1 ITS CONFIRMS BLT CONTEXT TRANSFER AS THE RIGHT PDP-6 PRIMITIVE

ITS SWITCH SAVES AC0..AC15 WITH ONE BLT AND COPIES OTHER CONTIGUOUS MACHINE
CONTEXT WITH ADDITIONAL BLTS.  RESTORE USES THE SAME APPROACH.  THIS STRONGLY
REINFORCES SECTION 10.2: DAIMOS'S LONG SCALAR MOVE/MOVEM RUNS IN
PROC_SAVE_USER, PROC_SAVE_KERNEL, PROC_RESTORE_USER, AND PROC_RESTORE_KERNEL
SHOULD BE REPLACED BY BLT WHERE THE CURRENT CONTEXT LAYOUT PERMITS IT.

NO NEW ARCHITECTURE IS REQUIRED FOR THIS CHANGE.  IT REMAINS ONE OF THE
STRONGEST IMMEDIATE KCORE TEXT-SIZE CANDIDATES.

### 11.2 ITS MAKES CONTINUATION-FREE BLOCKING EXPLICIT WITH ONE RESTART WORD

ITS FLSINS(U) IS A COMPACT PER-USER RESTART/WAIT WORD.  ZERO MEANS RUNNABLE;
OTHER FORMS REPRESENT AN I/O WAIT OR AN EXECUTIVE FLUSH/RESTART CONDITION.
UFLS RECORDS THE RESTARTABLE INSTRUCTION/CONTROL POINT, SCHEDULES ANOTHER USER,
AND LATER REENTERS THE OPERATION WITHOUT PRESERVING AN ARBITRARILY DEEP
EXECUTIVE STACK.

THIS CONFIRMS THAT THE SMALL PER-JOB EXECUTIVE STORAGE SEEN IN MONITOR 1.4 IS
AN INTENTIONAL ARCHITECTURAL ALTERNATIVE, NOT AN ACCIDENT OF THAT MONITOR.

FOR DAIMOS THIS REMAINS POST-0.9 WORK.  THE CURRENT PROC_WAIT_EVENT CONTRACT
ALLOWS DEEP FILESYSTEM/STORAGE CALL CHAINS TO SLEEP AND RESUME IN PLACE.  A
RESTART-WORD MODEL WOULD REQUIRE CONVERTING BLOCKING OPERATIONS INTO EXPLICIT
STATE MACHINES.  THE POTENTIAL PER-PROCESS RAM SAVING IS LARGE, BUT THE CHANGE
IS TOO INVASIVE FOR THE CURRENT FINAL SHRINK.

### 11.3 CONSIDER A CACHED CURRENT-PROCESS POINTER

ITS USES U AS THE DIRECT BASE/OFFSET OF THE CURRENT USER'S FIXED STATE BLOCK.
HOT PATHS THEREFORE ACCESS UPC(U), USTP(U), PIRQC(U), ETC. WITHOUT REPEATEDLY
RECOMPUTING A TABLE ADDRESS FROM A SMALL USER NUMBER.

DAIMOS KEEPS THE MORE COMPACT THREE-WORD PROC DESCRIPTOR, WHICH SHOULD NOT BE
GROWN TO A POWER-OF-TWO STRIDE.  HOWEVER, MANY KCORE PATHS REPEAT:

    MOVE  R,PROC_CURRENT_SLOT
    LSH   R,1
    ADD   R,PROC_CURRENT_SLOT
    ADD   R,PROC_TABLE

OR CALL PROC_SLOT_PTR FOR THE CURRENT SLOT.

REVISIT WHETHER ONE CACHED CURRENT-PROC POINTER CAN SAVE NET KCORE TEXT.  THE
POINTER WOULD BE UPDATED ONLY WHEN PROC_CURRENT_SLOT CHANGES.  DO NOT ADD A
NEW PER-PROCESS FIELD.  PREFER REUSING/ALIASING AN OTHERWISE DEAD PERMANENT
STATE WORD IF AVAILABLE, BUT ONLY WITH A PROVEN NON-OVERLAPPING LIFETIME.

THE EXPERIMENT MUST COUNT:

- INSTRUCTIONS REMOVED FROM ALL CURRENT-PROCESS ADDRESS CALCULATIONS.
- INSTRUCTIONS ADDED TO CONTEXT-SWITCH/IDLE TRANSITIONS.
- ANY PERMANENT BSS WORD REQUIRED.
- CALL SITES WHICH STILL NEED THE NUMERIC SLOT AND THEREFORE DO NOT BENEFIT.

CURRENT ASSESSMENT: MEDIUM-PRIORITY MEASURED KCORE EXPERIMENT.  DO NOT CHANGE
THE THREE-WORD PROC STRIDE JUST TO MAKE ADDRESSING CHEAPER.

### 11.4 ITS ONE-WORD I/O DESCRIPTORS SUGGEST A STORAGE-REQUEST PACKING AUDIT

ITS IOBFT USES ONE DENSE WORD PER DYNAMIC I/O BUFFER TO PACK LINKAGE,
OWNERSHIP/CHANNEL, MEMORY LOCATION, AND ACTIVE/FREE STATE.  ITS CAN DO THIS
BECAUSE ITS BUFFER MEMORY IS MANAGED AS A SEPARATE RESOURCE AND ITS WAIT MODEL
DOES NOT REQUIRE A PRIVATE SLEEPING STACK EVENT WORD FOR EACH REQUEST.

DAIMOS DSK/DRM RUNTIME REQUESTS CURRENTLY USE THREE PROCESS-STACK WORDS:

    WORD 0: DEVICE ADDRESS,,BUFFER ADDRESS
    WORD 1: READ/WRITE OPERATION
    WORD 2: COMPLETION EVENT (0 / +1 / -1)

THE OPERATION CONSUMES ONLY A TINY FRACTION OF WORD 1, SO AUDIT WHETHER
OPERATION AND COMPLETION CAN SHARE ONE WORD WITHOUT MAKING PROC_WAIT_EVENT OR
THE DRIVER HOT PATH LARGER.

DO NOT STEAL UNPROVEN ADDRESS BITS OR CREATE DEVICE-SPECIFIC POINTER TAGGING.
A CLEAN TWO-WORD DESCRIPTOR IS USEFUL ONLY IF THE COMPLETION predicate,
QUEUEING, WAKEUP, AND ACCOUNTING CODE REMAIN SIMPLE AND THE LINKED RESULT IS
SMALLER.  ONE WORD OF STACK SAVING BY ITSELF IS NOT ENOUGH TO JUSTIFY A
COMPLICATED EVENT ABI.

CURRENT ASSESSMENT: LOW-TO-MEDIUM PRIORITY; MEASURE AFTER THE LARGER BLT/PI
AND D6LZ STACK OPPORTUNITIES.

### 11.5 DIRECT PER-LEVEL PI SERVICE REINFORCES BOOT-LINKED PI CHAINS

ITS ASSIGNS RELATED DEVICES TO FIXED PI LEVELS AND OFTEN USES ONE LEVEL
ROUTINE TO POLL/SERVICE THE POSSIBLE SOURCES IN A KNOWN ORDER.  THERE IS NO
GENERAL RUNTIME LIST WALK FOR THE COMMON CASE.

DAIMOS SHOULD NOT BUILD MONOLITHIC ITS-STYLE DEVICE ROUTINES, BUT THIS FURTHER
SUPPORTS SECTION 10.1: THE SET OF RESIDENT PI HANDLERS IS KNOWN AFTER MINIT,
SO THE RUNTIME PATH SHOULD BE DIRECTLY LINKED/PATCHED RATHER THAN INTERPRETING
A RESIDENT TABLE/SPAN DESCRIPTION.

AFTER IMPLEMENTING LINKED PI CHAINS, RECHECK SAME-LEVEL HANDLERS FOR TINY
COMMON POLL/RETURN TAILS, ESPECIALLY CTY/GE AND SHARED STORAGE LEVELS.  SHARE
ONLY PROVEN COMMON HARDWARE/RETURN MECHANISM; DO NOT MERGE DEVICE SEMANTICS.

### 11.6 ITS PACKED DEVICE TABLE REINFORCES THE MONITORFS DESCRIPTOR AUDIT

ITS DEVTAB PACKS DIRECTION CAPABILITY, HANDLER SELECTION, AND A COMPACT DEVICE
NAME REPRESENTATION TOGETHER.  DAIMOS CORRECTLY AVOIDS A GENERAL DDB, BUT
MONITORFS CURRENTLY HAS A SEPARATE 19-WORD FULL SIXBIT NAME ARRAY WHILE DEVICE
TYPE/CAPABILITY KNOWLEDGE IS ENCODED IN RANGE TESTS AND SPECIAL CASES.

AS A MICRO-OPTIMIZATION, TEST WHETHER ONE SMALL PACKED MONITORFS DEVICE
DESCRIPTOR CAN REPLACE BOTH SOME NAME STORAGE AND SOME TYPE/CAPABILITY BRANCH
CODE.  MOST DEVICE NAMES ARE SHORT STEM+UNIT FORMS, BUT WCNSLS/OCNSLS/D6SET0
ARE EXCEPTIONS.  DO NOT FORCE A COMPLEX ENCODING FOR THOSE EXCEPTIONS.

THE CURRENT DIRECT FULL-WORD NAME ARRAY IS VERY FAST AND SIMPLE; KEEP IT IF
THE PACKED FORM DOES NOT WIN CLEARLY IN LINKED KCORE+BSS.

### 11.7 ITS DYNAMIC I/O MEMORY RECLAMATION IS ALREADY COVERED MORE SIMPLY

ITS CAN RECLAIM OR MOVE MEMORY BLOCKS USED FOR I/O BUFFERS UNDER CORE
PRESSURE, UPDATING ITS PACKED BUFFER DESCRIPTORS AS BLOCKS MOVE.  THIS IS A
POWERFUL CONSEQUENCE OF ITS CENTRAL I/O BUFFER POOL.

DAIMOS DOES NOT NEED THIS COMPLEXITY.  BCACHE IS CLEAN/DISCARDABLE, MEMFS
BACKING IS EVICTABLE, AND PROCESS SWAP + MEMFS SHARE BSTORE.  CURRENT DAIMOS
RECLAIM CLASSES ALREADY PROVIDE THE USEFUL MEMORY-PRESSURE BEHAVIOR WITHOUT
RELOCATING ACTIVE DRIVER BUFFERS.

CURRENT ASSESSMENT: KEEP DAIMOS DESIGN.

### 11.8 ITS STRUCTURE-OF-ARRAYS TTY STORAGE DOES NOT BEAT CURRENT DAIMOS

ITS KEEPS TERMINAL POINTERS, COUNTS, FLAGS, AND STATUS IN PARALLEL ARRAYS SO A
PI ROUTINE INDEXES ONLY THE FIELD IT NEEDS.  DAIMOS ALREADY USES A MORE
COMPACT HYBRID FOR ITS REQUIREMENTS:

- ONE PACKED PROC_TTY_RECORD WORD PER LOGICAL TTY.
- TWO 18-BIT CANONICAL-LINE BASES PER PROC_TTY_LINE_BASES WORD.
- CANONICAL LINE DATA IS DYNAMIC AND SIXBIT-PACKED ONLY WHEN REQUIRED.
- DCS/GE DEFER FOREIGN-LINE INPUT INTO THE EXISTING PACKED TTY RECORD RATHER
  THAN ALLOCATING PER-LINE DRIVER QUEUES.

THERE IS NO OBVIOUS ITS-DERIVED RAM REDUCTION HERE.  KEEP THE CURRENT DAIMOS
TTY REPRESENTATION UNLESS A FIELD-by-field census later proves unused bits or
direction-specific dead state.

### 11.9 ITS FIXED-STRIDE USER BLOCK SHOULD NOT REPLACE DAIMOS DYNAMIC U-AREAS

ITS CAN ADVANCE BETWEEN USERS WITH ADDI U,LUBLK BECAUSE EVERY USER OWNS ONE
FIXED-SIZE EXECUTIVE STATE BLOCK.  THIS MAKES ADDRESSING CHEAP BUT commits THE
FULL BLOCK FOR EVERY USER.

DAIMOS SHOULD KEEP THREE-WORD RESIDENT PROC DESCRIPTORS PLUS DYNAMIC U-AREAS.
THE BETTER APPLICATION OF THE ITS IDEA IS THE CURRENT-PROC POINTER EXPERIMENT,
NOT MAKING ALL PROCESS STORAGE FIXED OR POWER-OF-TWO STRIDED.

### 11.10 DIRECTION/TABLE-DRIVEN SYMMETRY IS A GENERAL REVIEW TECHNIQUE

ITS CORE COMPACTION USES SMALL DIRECTION TABLES (ACMDT*) SO THE SAME MOVEMENT
LOOP HANDLES UPWARD AND DOWNWARD CASES INSTEAD OF DUPLICATING LARGE ROUTINES.

WHEN DAIMOS HAS TWO SUBSTANTIAL ASSEMBLY PATHS DIFFERING ONLY BY A FEW
CONSTANTS, DIRECTIONS, OR CONTINUATIONS, COMPARE A SMALL DATA TABLE/PATCHED
SELECTOR AGAINST DUPLICATED CODE.  CURRENT LIKELY TARGETS REMAIN THE ALREADY
IDENTIFIED READ/WRITE STORAGE TAILS AND DSK/TAPE DCT SETUP; MM COMPACTION
ITSELF MOVES IN ONE DIRECTION AND DOES NOT NEED THIS ABSTRACTION.

### 11.11 REVISED CURRENT PRIORITIES AFTER ITS 138

ITS DOES NOT DISPLACE THE CHEAPER OPPORTUNITIES ALREADY RECORDED.  THE
MEASUREMENT ORDER IS NOW:

1. BLT PROCESS CONTEXT SAVE/RESTORE.
2. BOOT-LINK MULTI-HANDLER PI CHAINS.
3. REMOVE REDUNDANT PTR/PTP/CR/CP SOFTWARE BUSY WORDS.
4. FUSE MM FIT/FREE/FRAGMENTATION SCANS.
5. STORAGE MAP/READ/WRITE TAIL CONSOLIDATION.
6. COMMON DSK/TAPE DCT SETUP.
7. CACHED CURRENT-PROC POINTER EXPERIMENT.
8. DSK/DRM COMPLETION/WAIT COMMONALITY.
9. VFS/FILE-TABLE REPRESENTATION OPTIMIZATIONS.
10. SKIP-RETURN EXPERIMENTS FOR ASSEMBLY-ONLY HELPERS.
11. TWO-WORD STORAGE-REQUEST DESCRIPTOR EXPERIMENT ONLY IF SIMPLE.
12. PACKED MONITORFS DEVICE DESCRIPTOR/NAME EXPERIMENT.

THE HIGH-VALUE RAM TRACK REMAINS SEPARATE: FIRST TRY MOVING LARGE SHAREDABLE
STACK SCRATCH SUCH AS THE D6LZ 64-WORD REFILL WINDOW; ONLY AFTER THOSE LOCAL
WINS SHOULD DAIMOS CONSIDER THE MAJOR ITS/MONITOR-STYLE RESTARTABLE-BLOCKING
ARCHITECTURE.

## 9. JOSS-DERIVED SIZE-OPTIMIZATION CONCEPTS

JOSS IS PARTICULARLY RELEVANT BECAUSE IT WAS BUILT FOR THE PDP-6 AND THEREFORE
SHARES DAIMOS'S BASIC INSTRUCTION, CORE, AND DEVICE-CONTROL ECONOMICS.  ITS
MOST USEFUL LESSON IS LIMITED REENTRANCY COMBINED WITH AGGRESSIVE SHARING OF
SCARCE HARDWARE AND BUFFER RESOURCES.

DAIMOS ALREADY IMPLEMENTS MANY OF THE SAME IDEAS MORE GENERALLY: EXECUTIVE
CODE IS NOT TIMER-PREEMPTIBLE, OPTIONAL DEVICES LIVE IN MRES PACKAGES, THE
TYPE-136 PI ROUTER IS SHARED, FILESYSTEM PROVIDERS SHARE ONE SERIALIZED BLOCK
WORKSPACE, AND PROCESS QUEUES ARE INTRUSIVE AND STATE-DEPENDENT.

THE FOLLOWING REMAINING JOSS-DERIVED OPPORTUNITIES ARE WORTH MEASURING.

### 9.1 REMOVE REDUNDANT SOFTWARE BUSY WORDS FROM NON-SLEEPING POLLED DRIVERS

JOSS DELIBERATELY AVOIDS FULL REENTRANCY WHERE A CONTROL TRANSFER CAN BE
RESTRICTED TO A SMALL NUMBER OF SAFE POINTS.  DAIMOS HAS A DIRECTLY USEFUL
EQUIVALENT PROPERTY: ORDINARY EXECUTIVE CODE IS NOT PREEMPTED INTO ANOTHER
PROCESS; ONLY AN EXECUTIVE PATH WHICH EXPLICITLY SLEEPS CAN BE SWITCHED.

PTR, PTP, CR, AND CP CURRENTLY POLL THEIR HARDWARE SYNCHRONOUSLY WITH DEVICE
PI DISABLED AND DO NOT CALL PROC_WAIT_EVENT() OR ANOTHER RESCHEDULING PATH.
EACH NEVERTHELESS CARRIES A ONE-WORD SOFTWARE OWNERSHIP FLAG:

- PTR_STATE
- PTP_STATE
- CR_IOWD
- CP_IOWD

THESE WORDS CURRENTLY PROTECT AGAINST A SECOND PROCESS ENTERING THE SAME
SYNCHRONOUS DRIVER WHILE THE FIRST TRANSFER IS ACTIVE.  UNDER THE CURRENT
EXECUTIVE NON-PREEMPTION CONTRACT, SUCH A SECOND PROCESS CANNOT RUN UNTIL THE
FIRST CALL RETURNS.  LPT ALREADY USES THIS MODEL AND OWNS NO SOFTWARE BUSY
WORD, QUEUE, OR COMPLETION EVENT.

BEFORE REMOVAL, VERIFY FOR EACH DRIVER THAT:

- NO PI HANDLER CALLS BACK INTO THE BULK ENTRY.
- THE BULK ENTRY NEVER SLEEPS OR EXPLICITLY RESCHEDULES.
- NO INTERNAL KERNEL PATH CAN REENTER THE SAME DRIVER RECURSIVELY.
- HARDWARE BUSY/ERROR TESTS REMAIN INTACT WHERE THEY REPRESENT ACTUAL DEVICE
  STATE RATHER THAN SOFTWARE OWNERSHIP.

IF THE PROOF HOLDS, EACH DRIVER CAN DROP APPROXIMATELY ONE BSS WORD PLUS THE
ENTRY TEST, CLAIM, AND RELEASE INSTRUCTIONS.  ACROSS ALL FOUR INSTALLED
PACKAGES THE COMBINED SAVING IS ROUGHLY TWENTY WORDS, WITH SLIGHTLY FASTER
ENTRY/EXIT AS WELL.

EXPECTED VALUE: HIGH-CONFIDENCE, CHEAP MRES TEXT+BSS SAVING.

### 9.2 SHARE COMMON TYPE-136 / DATA-CONTROL TRANSFER SETUP

JOSS TREATS THE DISC/TAPE DATA CONTROL AS A RESOURCE IN ITS OWN RIGHT RATHER
THAN AS PART OF EITHER DEVICE.  DAIMOS ALREADY HAS THE CORRECT HIGH-LEVEL
BOUNDARY: DSK AND TAPE HAVE DIFFERENT MECHANICAL POLICIES, BUT SHARE STORAGE
OWNERSHIP AND THE TYPE-136 PI ROUTER.

DSK_IO.S AND TAPE_IO.S STILL CONTAIN NEARLY IDENTICAL LOW-LEVEL DCT SETUP:

    SELECT BLKI/BLKO VECTOR
    PUBLISH LOW-CORE DCT VECTOR
    PATCH COMPLETION CONTINUATION
    FORM -COUNT,,BUFFER-1 IOWD
    STORE STORAGE_IOWD

TAPE ADDS TAPE-SPECIFIC COUNT/EVENT INITIALIZATION, BUT THE DIRECT-TRANSFER
SETUP ITSELF IS COMMON HARDWARE MECHANISM.

INVESTIGATE A COMMON DCT SETUP PRIMITIVE ONLY IF LINKED KCORE+MRES SIZE
DECREASES.  DO NOT MOVE A HELPER PERMANENTLY INTO KCORE IF INDEPENDENTLY
OPTIONAL DSK/TAPE PACKAGES WOULD THEN FORCE EXTRA RESIDENT CODE.  CROSS-DOMAIN
P10FOLD OR AN ALREADY-MANDATORY SHARED STORAGE PACKAGE MAY BE BETTER PLACES TO
EXPLOIT THIS DUPLICATION.

KEEP DSK ELEVATOR LOGIC, TAPE MOTION/SEARCH LOGIC, AND THEIR COMPLETION STATE
MACHINES SEPARATE.

EXPECTED VALUE: SMALL TO LOW-TENS OF WORDS IF THE COMMON ANCHOR CAN BE SHARED
WITHOUT GROWING THE ALWAYS-RESIDENT DOMAIN.

### 9.3 CLASSIFY EVERY DRIVER STATE WORD BY WHY IT EXISTS

THE PTR/PTP/CR/CP RESULT SUGGESTS A GENERAL DRIVER AUDIT.  CLASSIFY EACH
PERSISTENT DRIVER WORD INTO ONE OF THREE GROUPS:

1. HARDWARE/PI COMPLETION STATE, NEEDED ASYNCHRONOUSLY.
2. STATE WHICH MUST SURVIVE A SLEEPING EXECUTIVE CONTINUATION.
3. SOFTWARE OWNERSHIP USED ONLY TO PREVENT ANOTHER PROCESS ENTERING A
   NON-SLEEPING EXECUTIVE PATH.

GROUPS 1 AND 2 ARE REAL PERSISTENT STATE.  GROUP 3 IS A SIZE CANDIDATE UNDER
THE CURRENT NON-PREEMPTIBLE EXECUTIVE MODEL.

KNOWN EXAMPLES WHICH MUST REMAIN INCLUDE CTY RX/TX PENDING STATE, DPY PENDING,
DSK/DRM REQUEST STATE, AND TAPE COMPLETION/MOTION STATE.  DO NOT REMOVE STATE
USED BY PI HANDLERS OR ACROSS PROC_WAIT_EVENT().

### 9.4 USE EXPLICIT SLEEP BOUNDARIES IN U-AREA/STACK OPTIMIZATION

JOSS EXPLAINS WHY FULL REENTRANCY CAN COST MORE memory: arbitrary interruption
points require more user-owned context.  DAIMOS'S CONTROLLED EXECUTIVE
PREEMPTION GIVES A STRONGER RULE FOR THE U-AREA/STACK AUDIT INTRODUCED IN THE
FUZIX SECTION.

PARTITION KERNEL PATHS BY WHETHER THEY CAN SLEEP:

    NON-SLEEPING EXECUTIVE PATH
        -> NO PROCESS SWITCH DURING THE CALL
        -> TRANSIENT STATE SHOULD PREFER ACS/SHORT STACK FRAMES
        -> NO PROCESS-EXCLUSION FLAG IS NEEDED SOLELY FOR SCHEDULER CONCURRENCY

    SLEEPING EXECUTIVE PATH
        -> CONTINUATION MAY RESUME MUCH LATER
        -> ONLY STATE LIVE ACROSS THE SLEEP NEEDS STABLE U-AREA/STACK STORAGE

THIS SHOULD GUIDE ANY ATTEMPT TO SHRINK PROC_UAREA_WORDS.  DO NOT MAKE MORE
ROUTINES FULLY REENTRANT MERELY TO SHARE SCRATCH; USE THE EXISTING CONTROLLED
SLEEP POINTS AS LIFETIME BOUNDARIES.

### 9.5 JOSS SHARED DEVICE BUFFER POOL IS A PRINCIPLE, NOT A DAIMOS FEATURE

JOSS USES ONE AVAILABLE-BUFFER LIST FOR USER CONSOLE I/O, OPERATOR TTY, AND
TAPE OUTPUT.  A SMALL CONTEXT NUMBER SELECTS THE DEVICE-SPECIFIC START ROUTINE.
THIS IS STRONGER SHARING THAN SEPARATE PER-DEVICE BUFFER QUEUES.

DAIMOS CURRENTLY DOES BETTER FOR ITS LOW-RATE DEVICES: PTR/PTP/CR/CP/LPT AND
SEVERAL OTHER DRIVERS USE CALLER-OWNED BUFFERS OR NO DATA BUFFER AT ALL.
ADDING A JOSS-LIKE COMMON RESIDENT BUFFER POOL WOULD INCREASE RAM.

RETAIN THE JOSS PRINCIPLE FOR FUTURE ASYNCHRONOUS BUFFERED DEVICES: IF SEVERAL
DEVICES EVER REQUIRE KERNEL-OWNED QUEUED OUTPUT, PREFER ONE COMMON POOL WITH A
SMALL DEVICE CONTEXT OVER SEPARATE BUFFER POOLS.

### 9.6 SHARED SCRATCH UNDER LIMITED REENTRANCY IS ALREADY A DAIMOS STRENGTH

JOSS REUSES SHARED BUFFERS BECAUSE ITS SUPERVISOR RESTRICTS SIMULTANEOUS USE.
DAIMOS'S FS_BLOCK_WORKSPACE APPLIES THE SAME IDEA TO FILESYSTEM PROVIDERS:
D6FS, DTFS, TSFS, MEMFS SNAPSHOT OPERATIONS, AND STORAGE BOOT HELPERS SHARE ONE
0200-WORD WORKSPACE UNDER PROVIDER SERIALIZATION.

KEEP THIS DESIGN.  AS A REVIEW RULE, ANY NEW LARGE SCRATCH BUFFER IN A
SERIALIZED SUBSYSTEM SHOULD EXPLAIN WHY IT CANNOT USE AN EXISTING MUTUALLY
EXCLUSIVE WORKSPACE.

### 9.7 JOSS CORE-MAP BACKLINKS ARE NOT A GOOD DAIMOS TRADE

JOSS STORES BOTH USER->CORE AND CORE->USER REFERENCES EVEN THOUGH THEY ARE
REDUNDANT, BECAUSE ITS CORE MAP IS A FIXED ARRAY OF 1024-WORD BLOCKS AND THE
BACKLINK AVOIDS SEARCHES.

DAIMOS ALREADY KEEPS THE IMPORTANT DIRECT PROCESS->PHYSICAL-BASE RELATION IN
VM_STATE RH.  MM_EXTENTS[] IS A COMPACT SORTED ARRAY OF VARIABLE EXTENTS, AND
INSERTION/DELETION SHIFTS ARRAY INDICES.  ADDING A CACHED PROCESS->EXTENT INDEX
WOULD REQUIRE BACKLINK MAINTENANCE WHEN THE ARRAY MOVES AND WOULD LIKELY COST
MORE CODE/STATE THAN SCANNING AT MOST MM_MAX_EXTENTS ENTRIES.

CURRENT ASSESSMENT: DO NOT ADD EXTENT-INDEX BACKLINKS.

### 9.8 JOSS RESOURCE STATES DO NOT REPLACE DAIMOS WAIT CHANNELS

JOSS ENCODES RESOURCE WAIT REASONS DIRECTLY AS MANY USER STATES AND QUEUES.
THIS IS COMPACT FOR A FIXED-PURPOSE SERVICE.  DAIMOS'S STATE + WAIT-CLASS +
WAIT-CHANNEL REPRESENTATION IS MORE GENERAL WHILE STILL USING THE THREE-WORD
PROCESS DESCRIPTOR AND INTRUSIVE QUEUES.

DO NOT CREATE ONE PROCESS STATE PER DEVICE OR RESOURCE CONDITION.  THE CURRENT
STATE-DEPENDENT SCHED RH REUSE IS ALREADY THE BETTER GENERAL-PURPOSE DESIGN.

### 9.9 SELF-PATCHED CONTINUATIONS REMAIN A VALID PDP-6 SIZE TECHNIQUE

JOSS FREQUENTLY USES SMALL PATCHED CONTINUATIONS/STATE SELECTORS IN PLACE OF
ENUM-DECODE BRANCH CHAINS.  DAIMOS ALREADY USES THE SAME TECHNIQUE IN DSK AND
TAPE DCT STATE MACHINES.

WHEN REVIEWING A SMALL RESIDENT STATE MACHINE WITH TWO OR THREE MUTUALLY
EXCLUSIVE CONTINUATIONS, COMPARE A SELF-PATCHED JRST/ADDRESS AGAINST EXPLICIT
STATE TESTS.  RETAIN THE PATCHED FORM ONLY WHEN IT IS SMALLER AND DOES NOT
COMPLICATE PI SAFETY.

### 9.10 JOSS STARTUP OVERLAY IS ALREADY SUPERSEDED BY KINIT RECLAMATION

JOSS OVERLAYS STARTUP/RECOVERY SUPERVISOR PARTS AFTER INITIALIZATION.  DAIMOS
KINIT RECLAMATION IS THE MORE GENERAL FORM OF THE SAME IDEA.

DO NOT INTRODUCE A SPECIAL JOSS-STYLE OVERLAY.  INSTEAD CONTINUE TO AUDIT THAT
BOOT/DIAGNOSTIC/RECOVERY-ONLY CODE AND SCRATCH DO NOT REMAIN PERMANENT AFTER
THEIR INVARIANTS HAVE BEEN ESTABLISHED.

## 12. SELF-MODIFYING CODE AS A SIZE-OPTIMIZATION TOOL

PDP-6 CODE MODIFICATION IS NOT ONLY A STATE-MACHINE TECHNIQUE.  IT CAN ALSO
BE USED TO TURN ALMOST-IDENTICAL ROUTINES INTO LITERALLY IDENTICAL ROUTINES SO
THAT ONE BODY CAN BE SHARED OR P10FOLD CAN FOLD IT.

THE IMPORTANT QUESTION IS THEREFORE NOT ONLY:

    ARE THESE TWO BLOCKS IDENTICAL ENOUGH TO FOLD NOW?

BUT ALSO:

    CAN THE FEW DIFFERING WORDS BECOME PATCHED PARAMETERS SO THE LARGE
    REMAINDER BECOMES IDENTICAL?

THIS SHOULD BECOME AN EXPLICIT PART OF FUTURE SIZE CENSUSES.

### 12.1 PREFER INITIALIZATION-TIME SPECIALIZATION

THE SAFEST AND CHEAPEST FORM IS CODE PATCHED ONCE BY KINIT/MINIT AFTER
HARDWARE, FILESYSTEM PERSONALITY, OR MODULE CONFIGURATION IS KNOWN.

DAIMOS ALREADY USES THIS STYLE EXTENSIVELY:

- KCORE/MRES CALL AND JRST SLOTS ARE PATCHED TO INSTALLED SERVICES.
- SINGLE-HANDLER PI LEVELS ARE PATCHED DIRECTLY TO THEIR HANDLER.
- DSK/DRM/STORAGE BACKENDS USE PATCHED READ/WRITE TAILS.
- DTFS PATCHES PER-MOUNT PERSONALITY INSTRUCTIONS AND EXECUTES THEM WITH XCT.

INITIALIZATION-TIME PATCHING IS PARTICULARLY ATTRACTIVE BECAUSE THE CODE WHICH
COMPUTES AND INSTALLS THE SPECIALIZATION LIVES IN RECLAIMABLE KINIT/MINIT.
THE RUNTIME PAYS ONLY THE FINAL SPECIALIZED WORD OR SMALL PATCH TABLE.

USE THIS BEFORE ADDING A PERMANENT RUNTIME DISPATCH TABLE WHEN THE CHOICE IS
FIXED AFTER INITIALIZATION.

### 12.2 PATCH-TO-FOLD: MOVE THE DIFFERENCES OUT OF THE LARGE BODY

WHEN TWO ROUTINES ARE IDENTICAL EXCEPT FOR ONE OR A FEW WORDS, CONSIDER
MOVING THOSE WORDS INTO PER-INSTANCE PATCH CELLS OR TINY VENEERS.

EXAMPLE SHAPE BEFORE:

    BODY A:  A A A X A A A A A
    BODY B:  A A A Y A A A A A

INSTEAD OF RETAINING TWO NINE-WORD BODIES, USE:

    PARAM A: X
    PARAM B: Y
    COMMON:  A A A [PARAMETERIZED STEP] A A A A A

THE PARAMETERIZED STEP MAY BE:

- XCT OF A PATCHED INSTRUCTION WORD.
- A PATCHED JRST/PUSHJ VENEER.
- A PATCHED IMMEDIATE OR EFFECTIVE-ADDRESS FIELD.
- A SMALL PER-INSTANCE PREFIX/SUFFIX WHICH ENTERS ONE COMMON MIDDLE BODY.

THIS IS USEFUL EVEN WHEN THE EXTRA XCT/JRST COSTS ONE EXECUTED INSTRUCTION IF
THE SAVED BODY IS COLD OR THE NET PERMANENT-WORD SAVING IS MATERIAL.  FOR HOT
PATHS, REQUIRE A STRONGER SIZE WIN BEFORE ACCEPTING EXTRA EXECUTION COST.

DTFS_PERSONALITY_XCT IS THE EXISTING DAIMOS PROOF OF CONCEPT: MOUNT-TIME
SPECIALIZATION IS STORED AS AN INSTRUCTION, AND ONE COMMON RUNTIME ROUTINE XCTS
THE SELECTED INSTRUCTION INSTEAD OF CARRYING SEPARATE PERSONALITY BODIES.

### 12.3 ALMOST-FOLDABLE CODE SHOULD BE A TOOLING CATEGORY

P10FOLD CURRENTLY FINDS EXACT RELOCATION-AWARE FOLDING OPPORTUNITIES.  FUTURE
P10SUPER/P10FOLD ANALYSIS SHOULD ALSO REPORT NEAR-CLONES WHICH WOULD BECOME
FOLDABLE AFTER PARAMETERIZING A SMALL NUMBER OF WORDS.

A USEFUL NEAR-FOLD REPORT SHOULD IDENTIFY BLOCK PAIRS WITH:

- EQUAL LENGTH OR A LARGE EQUAL SUBRANGE.
- ONE TO A SMALL NUMBER OF MISMATCHED WORDS.
- THE TYPE OF EACH MISMATCH:
  - OPCODE.
  - AC FIELD.
  - IMMEDIATE VALUE.
  - EFFECTIVE ADDRESS.
  - BRANCH/CALL TARGET.
- WHETHER THE DIFFERENCE IS BOOT-CONSTANT, MOUNT-CONSTANT, DEVICE-CONSTANT,
  OR TRUE PER-CALL STATE.
- ESTIMATED NET SAVING AFTER ADDING PATCH CELLS, XCTS, OR VENEERS.

THE TOOL SHOULD NOT AUTOMATICALLY REWRITE SOURCE.  IT SHOULD FIRST ANSWER:

    IF N DIFFERING WORDS ARE EXTERNALIZED, HOW MANY WORDS OF COMMON BODY
    BECOME FOLDABLE?

THIS IS A NATURAL EXTENSION OF THE EXISTING CROSS-DOMAIN P10FOLD CENSUS.

### 12.4 BOOT-CONSTANT DIFFERENCES ARE THE BEST TARGET

THE BEST NEAR-CLONES ARE THOSE WHOSE DIFFERENCE IS FIXED FOR THE WHOLE BOOT:

- INSTALLED DEVICE SERVICE ADDRESS.
- PI NEXT-HANDLER TARGET.
- ROOT STORAGE BACKEND.
- HARDWARE UNIT/CONTROLLER CHOICE.
- READ/WRITE HARDWARE VECTOR WHEN A ROUTINE INSTANCE HAS A FIXED DIRECTION.
- OPTIONAL FEATURE PRESENT/ABSENT.

THESE CAN OFTEN BE PATCHED ONCE AND THEN EXECUTE WITHOUT A RUNTIME TEST.

THE NEXT-BEST CLASS IS MOUNT-CONSTANT OR OBJECT-CONSTANT DATA, WHERE A SMALL
PATCHED INSTRUCTION ARRAY CAN BE INDEXED/XCTED AS DTFS ALREADY DOES.

PER-CALL DIFFERENCES ARE LESS ATTRACTIVE BECAUSE THE PATCHING ITSELF BECOMES
PART OF THE HOT PATH AND MAY REQUIRE SERIALIZATION.

### 12.5 RUNTIME SELF-MODIFICATION IS SAFE ONLY UNDER A STRONG EXCLUSION PROOF

A SHARED CODE WORD MUST NOT BE MODIFIED WHILE ANOTHER PROCESS OR PI HANDLER
CAN EXECUTE OR OBSERVE IT IN AN INCOMPATIBLE STATE.

RUNTIME PATCHING IS ACCEPTABLE ONLY WHEN ONE OF THESE HOLDS:

- THE PATCH IS DONE BEFORE PI/USER EXECUTION STARTS.
- THE CODE IS PRIVATE TO ONE MODULE INSTANCE AND CANNOT RUN CONCURRENTLY.
- THE ENCLOSING EXECUTIVE PATH IS NON-SLEEPING AND NON-PREEMPTIBLE AND NO PI
  HANDLER ENTERS THE PATCHED REGION.
- AN EXISTING SERIALIZATION LOCK ALREADY EXCLUDES ALL OTHER USERS FOR THE
  ENTIRE PATCH-AND-EXECUTE INTERVAL.

DO NOT ADD A NEW LOCK SOLELY TO ENABLE A SMALL SELF-MODIFYING-CODE SAVING.
THAT USUALLY DEFEATS BOTH SIZE AND SIMPLICITY.

WHEN CONCURRENCY EXISTS, PREFER PER-INSTANCE PATCH WORDS + XCT OR A SMALL
PATCHED VENEER OVER MUTATING ONE COMMON EXECUTING BODY.

### 12.6 PATCHED INSTRUCTION WORDS CAN REPLACE BRANCH CHAINS

IF A HOT/COLD STATE CHOICE HAS ONLY A FEW POSSIBLE ACTIONS, A PATCHED
INSTRUCTION CAN REPRESENT THE STATE DIRECTLY:

    SELECTOR: JRST TARGET

OR:

    OPERATION: DATAO/CONO/MOVEI/... WITH PATCHED EA OR IMMEDIATE

THIS CAN REMOVE:

- ENUM LOADS.
- COMPARES.
- MULTI-WAY BRANCH CHAINS.
- SMALL HANDLER TABLES.

DSK_DCT_SELECT AND TAPE_DCT_SELECT ALREADY USE THIS PATTERN.  THE PROPOSED
BOOT-LINKED PI HANDLER CHAINS ARE ANOTHER INSTANCE OF THE SAME IDEA.

### 12.7 NEAR-FOLD TARGETS TO CHECK IN DAIMOS

THE FIRST TARGETS FOR A PATCH-TO-FOLD CENSUS SHOULD BE:

1. DSK AND TAPE DCT SETUP/COMPLETION PATHS.
2. DSK270 AND DRM236 READ/WRITE ENTRY/GATEWAY PATHS.
3. FS_BACKING, BLOCKSET, BADMAP, AND LOGSTORE BACKEND TAILS.
4. PI HANDLERS WHOSE BODIES DIFFER MAINLY IN DEVICE TEST/ACK INSTRUCTIONS.
5. FILESYSTEM PROVIDER DISPATCHERS WITH IDENTICAL CONTROL FLOW BUT DIFFERENT
   SERVICE VECTOR OR CONTEXT SOURCE.
6. READ/WRITE OR INPUT/OUTPUT PAIRS WHICH DIFFER ONLY IN ONE OPERATION WORD,
   HARDWARE VECTOR, OR ACCOUNTING TARGET.
7. KCC-GENERATED CODE WHERE EQUIVALENT BODIES DIFFER ONLY IN AC CHOICE,
   BRANCH ORIENTATION, OR CONSTANT MATERIALIZATION.

DO NOT FORCE PARAMETERIZATION WHEN THE COMMON PORTION IS ONLY A FEW WORDS.
THE TECHNIQUE IS MOST ATTRACTIVE WHEN ONE OR TWO PATCH WORDS ENABLE A LARGE
BODY, ESPECIALLY 8-20+ WORDS, TO BE SHARED.

### 12.8 SELF-MODIFICATION CAN ENABLE CROSS-DOMAIN FOLDING WITHOUT A GENERAL ABI

SOME KCORE/MRES ROUTINES MAY BE NEAR-IDENTICAL BUT CANNOT SHARE A NORMAL
CALLABLE HELPER WITHOUT ADDING CALL/RETURN OVERHEAD OR NEW REGISTER
CONVENTIONS.  A TINY PATCHED PREFIX/SUFFIX CAN SOMETIMES PRESERVE EACH
EXISTING CALLING CONVENTION WHILE MAKING THE LARGE INTERNAL BODY IDENTICAL.

THIS IS ESPECIALLY INTERESTING FOR P10FOLD EXTERNAL-ANCHOR WORK:

- KEEP THE ORIGINAL ENTRY POINTS.
- LEAVE INSTANCE-SPECIFIC SETUP IN 1-3 WORD VENEERS.
- NORMALIZE THE LARGE BODY TO AN IDENTICAL SEQUENCE.
- FOLD ONE BODY INTO THE OTHER OR ANCHOR MRES AGAINST KCORE.

THE SAVING MUST BE CALCULATED AFTER ALL VENEERS AND PATCH WORDS.  DO NOT COUNT
THEORETICAL COMMON BODY SIZE ALONE.

### 12.9 CONSIDER PATCHING AC/EA FIELDS, NOT ONLY WHOLE JRSTS

PDP-6 INSTRUCTIONS ARE ONE 36-BIT WORD WITH COMPACT OPCODE, AC, INDIRECT,
INDEX, AND ADDRESS FIELDS.  IF TWO NEAR-CLONES DIFFER ONLY IN ONE FIELD, MINIT
OR MOUNT SETUP MAY PATCH ONLY THAT FIELD RATHER THAN KEEPING TWO WHOLE
ROUTINES.

POSSIBLE EXAMPLES INCLUDE:

- EFFECTIVE ADDRESS OF A COUNTER OR DEVICE STATE WORD.
- AC NUMBER USED AS A DEVICE-SPECIFIC SCRATCH REGISTER.
- ADDRESS OF A BACKEND ENTRY.
- SMALL IMMEDIATE OPERATION SELECTOR.

FIELD PATCHING IS MOST USEFUL WHEN IT ELIMINATES AN OTHERWISE DUPLICATED
MULTIWORD BODY.  DO NOT USE IT MERELY TO SAVE ONE CONSTANT LOAD IF THE PATCH
MECHANISM MAKES THE CODE HARDER TO AUDIT.

### 12.10 DOCUMENT PATCH SITES AS PART OF THE ABI

EVERY SELF-MODIFIED WORD SHOULD HAVE A SINGLE EXPLICIT OWNER AND DOCUMENT:

- WHO PATCHES IT.
- WHEN IT MAY BE PATCHED.
- WHICH FIELD OR WHOLE INSTRUCTION IS MUTABLE.
- WHAT INVARIANT MAKES CONCURRENT EXECUTION SAFE.
- WHETHER THE WORD IS KCORE, MRES, PER-MOUNT DATA, OR TRANSIENT KINIT.

THIS IS IMPORTANT FOR P10FOLD/P10SUPER TOO: THE TOOLS MUST KNOW THAT A PATCHED
WORD IS INTENTIONALLY NON-CONSTANT AND MUST NOT FOLD IT INTO AN INCOMPATIBLE
SHARED LOCATION.

### 12.11 PRIORITY RULE FOR PATCH-TO-FOLD WORK

USE THIS ORDER:

1. EXACT ZERO-COST P10FOLD.
2. SOURCE CANONICALIZATION WHICH MAKES CODE EXACTLY FOLDABLE WITH NO RUNTIME
   COST.
3. KINIT/MINIT-TIME PATCHING WHICH MAKES A LARGE BODY FOLDABLE.
4. PER-INSTANCE PATCH WORD + XCT/VENEER WHEN THE BODY SAVING IS MATERIAL.
5. RUNTIME SELF-MODIFICATION ONLY WHEN EXISTING SERIALIZATION/NON-PREEMPTION
   MAKES IT FREE OF NEW LOCKING AND THE MEASURED SAVING JUSTIFIES THE COST.

THIS KEEPS SELF-MODIFYING CODE A SIZE TOOL RATHER THAN A SOURCE OF GENERAL
RUNTIME COMPLEXITY.

## 13. LATER ITS 1644-1652 SIZE-OPTIMIZATION LESSONS

THE LATER ITS SOURCE LINE FROM 1644 THROUGH 1652 IS ARCHITECTURALLY VERY
CONSERVATIVE.  THE CORE IDEAS ALREADY PRESENT IN ITS 138 -- FIXED-STRIDE USER
STATE, EXECUTABLE FLSINS WAIT CONDITIONS, ONE-WORD I/O BUFFER DESCRIPTORS,
PACKED DEVICE TABLES, BLT CONTEXT TRANSFER, AND HEAVY INITIALIZATION/RUNTIME
PATCHING -- REMAIN IN PLACE.  MOST 1644-1652 CHANGES ARE HARDWARE SUPPORT,
CONFIGURATION, OR BUG FIXES RATHER THAN NEW KERNEL-SIZE ARCHITECTURE.

THAT STABILITY IS ITSELF USEFUL EVIDENCE: THESE REPRESENTATIONS SURVIVED A
MUCH LARGER AND MORE FEATUREFUL ITS WITHOUT BEING REPLACED BY GENERAL OBJECT
LAYERS.

THERE ARE, HOWEVER, A FEW LATER REFINEMENTS WHICH ADD TO THE DAIMOS SIZE
TOOLBOX.

### 13.1 PACK COLD CONTROL DISPATCH AS METADATA, NOT FULL INSTRUCTION TABLES

ITS 138 IMPLEMENTS USER-VARIABLE ACCESS WITH TWO PARALLEL FULL-INSTRUCTION
TABLES: ONE TABLE FOR READ OPERATIONS AND ANOTHER FOR WRITE OPERATIONS.  LATER
ITS REPLACES THIS WITH ONE UENTRY WORD PER VARIABLE.

EACH UENTRY PACKS:

- FOUR SMALL ACCESS-METHOD FIELDS FOR OWN/INFERIOR READ AND WRITE.
- A COMPACT ROUTINE OR RELATIVE-FIELD VALUE FOR THE EXCEPTIONAL CASE.
- A SECOND COMPACT ROUTINE OR RELATIVE-FIELD VALUE.

THE SHARED INTERPRETER THEN IMPLEMENTS COMMON DIRECT-FIELD GET/SET OPERATIONS,
WHILE ONLY SPECIAL CASES BRANCH TO DEDICATED ROUTINES.

THIS IS A GENERAL SIZE RULE FOR COLD CONTROL-PLANE OPERATIONS:

    MANY TINY NEAR-IDENTICAL HANDLERS
        -> SMALL METHOD DESCRIPTOR + ONE SHARED INTERPRETER

IT IS NOT APPROPRIATE FOR HOT DEVICE DATA PATHS WHERE INTERPRETING METADATA
WOULD ADD EXECUTION COST TO EVERY WORD/CHARACTER TRANSFER.

### 13.2 PROC_CONTROL_TABLE IS A CONCRETE HALFWORD-PACKING CANDIDATE

DAIMOS PROC_CONTROL CURRENTLY HAS 26 FULL 36-BIT DISPATCH WORDS FOR OPCODES
000..031, INCLUDING FIVE IDENTICAL KRET_NEG1 RESERVED ENTRIES.

ALL KCORE HANDLER ADDRESSES FIT IN 18 BITS.  THE MAIN NATIVE-SYSCALL AND
EXTENSION DISPATCH TABLES ALREADY STORE TWO HANDLER ADDRESSES PER WORD, SO
PROC_CONTROL_TABLE SHOULD BE MEASURED WITH THE SAME REPRESENTATION.

CURRENT FORM:

    26 TABLE WORDS
    + 1 INDIRECT JRST

A STRAIGHT HALFWORD TABLE NEEDS 13 WORDS PLUS A SMALL HALF-SELECT SEQUENCE.
USING THE SAME GENERAL SHAPE AS EXEC_NATIVE_SYSCALL SHOULD STILL SAVE ROUGHLY
HALF A DOZEN PERMANENT KCORE WORDS AFTER SELECTOR OVERHEAD.

DO NOT COMPLICATE THE FIRST EXPERIMENT BY SPECIAL-CASING THE FIVE RESERVED
020..024 ENTRIES; HALFWORD-PACK THEM AS KRET_NEG1 FIRST.  REMOVE THE HOLE ONLY
IF A SECOND MEASUREMENT SHOWS THAT ITS RANGE-REMAP CODE SAVES ADDITIONAL
WORDS.

EXPECTED VALUE: CHEAP, LOW-RISK, SMALL KCORE WIN.

### 13.3 ONLY THEN TEST A UENTRY-LIKE PROCCTL METHOD DESCRIPTOR

SEVERAL PROCCTL OPERATIONS ARE SIMPLE QUERIES OR FIELD UPDATES, WHILE OTHERS
ARE GENUINELY SPECIAL:

- GETPGRP, GETSESSION, GETDOMAIN, GETTTY, GETUID, GETGID, GETMODE AND SIMILAR
  QUERIES HAVE REGULAR FIELD-EXTRACTION SHAPES.
- SESSION/DOMAIN CREATION, EVENT DELIVERY, TTY ATTACHMENT, OWNERSHIP CHECKS,
  AND CREDENTIAL CHANGES NEED SPECIAL POLICY CODE.

AFTER HALFWORD-PACKING THE DISPATCH TABLE, MEASURE WHETHER A VERY SMALL METHOD
DESCRIPTOR CAN REPLACE ENOUGH OF THE SIMPLE LEAF HANDLERS TO WIN FURTHER.

A POSSIBLE DESCRIPTOR WOULD NEED ONLY INFORMATION SUCH AS:

- SOURCE CLASS: PROC WORD / U-AREA WORD / TTY RECORD / SPECIAL ROUTINE.
- WORD OFFSET OR SPECIAL ROUTINE ADDRESS.
- WHOLE WORD / LH / RH / SMALL BYTE FIELD.
- WHETHER ARG MUST BE ZERO.

DO NOT BUILD A GENERAL REFLECTION OR STRUCT-FIELD ENGINE.  IF THE INTERPRETER
AND DESCRIPTORS DO NOT BEAT THE EXISTING SHORT HANDLERS IN LINKED KCORE, KEEP
THE HANDWRITTEN CODE.

### 13.4 PACK HANDLER FLAGS WITH THE HANDLER ADDRESS WHEN THE HALF IS FREE

LATER ITS IOTTB ENTRIES COMBINE MODE/CAPABILITY FLAGS WITH THE ROUTINE ADDRESS
IN ONE WORD.  THE DISPATCHER TESTS THE FLAG HALF AND THEN JUMPS THROUGH THE
ADDRESS HALF.  NO PARALLEL CAPABILITY TABLE IS REQUIRED.

DAIMOS ALREADY USES THIS PRINCIPLE IN MANY PLACES -- PACKED VECTORS, VNODES,
PROCESS WORDS, FILE METADATA, AND TWO-ADDRESS DISPATCH WORDS -- SO THIS IS NOT
A NEW SUBSYSTEM.  IT SHOULD BE AN AUDIT RULE FOR EVERY REMAINING POINTER
TABLE:

    IF AN ADDRESS USES ONLY ONE 18-BIT HALF, CAN THE OTHER HALF HOLD FLAGS,
    A SECOND ADDRESS, OR A SMALL CONSTANT CURRENTLY STORED ELSEWHERE?

THE PROC_CONTROL TABLE IS THE CLEAREST CURRENT MISSED INSTANCE.

### 13.5 EXECUTABLE WAIT STATE IS A VALID SELF-MODIFYING REPRESENTATION

FLSINS EXISTS ALREADY IN ITS 138 AND IS RETAINED IN LATER ITS.  A BLOCKED
USER'S ONE-WORD WAIT STATE IS AN ACTUAL PDP-10 INSTRUCTION.  THE SCHEDULER
EXECUTES IT WITH XCT:

    XCT FLSINS(U)

THE INSTRUCTION TESTS THE RESOURCE CONDITION DIRECTLY AND ITS SKIP BEHAVIOR
ENCODES WHETHER THE USER REMAINS BLOCKED OR WAKES AT A PARTICULAR PRIORITY.

THIS IS AN IMPORTANT SELF-MODIFYING/DATA-AS-CODE IDEA FOR ANY FUTURE
RESTARTABLE-BLOCKING DAIMOS DESIGN: A ONE-WORD BLOCKED-OPERATION RECORD CAN BE
THE TEST ITSELF INSTEAD OF AN ENUM WHICH REQUIRES A GENERIC SWITCH.

IT SHOULD NOT REPLACE DAIMOS PROC_WAIT_EVENT TODAY.  DAIMOS MAINTAINS AN
INTRUSIVE RUN QUEUE AND WAKES EVENT WAITERS WHEN THE EVENT CHANGES, WHILE ITS
SCANS USERS DURING SCHEDULING.  COPYING FLSINS DIRECTLY WOULD TRADE AWAY THE
CURRENT O(1)-STYLE RUN-QUEUE SELECTION FOR REPEATED BLOCKED-PROCESS TESTS.

CURRENT ASSESSMENT: KEEP AS A POST-0.9 RESTARTABLE-BLOCKING REPRESENTATION
OPTION, NOT A CURRENT SCHEDULER CHANGE.

### 13.6 LATER ITS USES A SMALL ABSOLUTE CURRENT-CONTEXT SHADOW BLOCK

LATER ITS KEEPS A VERY SMALL UEXIT..UEXND BLOCK AT FIXED EXECUTIVE ADDRESSES
AND BLT-COPIES THE CORRESPONDING PER-USER WORDS INTO/OUT OF THAT BLOCK DURING
SCHEDULING.  THIS GIVES HOT EXECUTIVE CODE CHEAP ABSOLUTE REFERENCES WITHOUT
MAKING ALL PER-USER STATE GLOBAL.

DAIMOS HAS A FEW ANALOGOUS CURRENT-PROCESS GLOBALS -- MACH_USER_SP,
MACH_KERNEL_SP, MACH_SYSCALL_SAVE, FILE_TABLE, AND PI RETURN STATE -- BUT THEY
ARE DELIBERATELY SCATTERED OR ALIASED WITH OTHERWISE DEAD MONITORFS COUNTER
SLOTS TO SAVE BSS.  MOVING THEM INTO A NEW CONTIGUOUS SHADOW BLOCK MAY LOSE
THOSE EXISTING RAM SAVINGS.

THEREFORE DO NOT INTRODUCE A SHADOW BLOCK FIRST.  AFTER BLT AC CONTEXT
SAVE/RESTORE IS IMPLEMENTED, RECOUNT THE REMAINING SCALAR CONTEXT-SWITCH
MOVES.  ONLY IF ENOUGH CONTIGUOUS CURRENT-PROCESS WORDS REMAIN SHOULD THEIR
LAYOUT BE CHANGED TO ENABLE ONE SMALL BLT.

EXPECTED VALUE: POSSIBLE SMALL TEXT WIN; LIKELY NOT WORTH EXTRA BSS UNLESS
EXISTING ALIASING CAN BE PRESERVED.

### 13.7 LATER-PDP-10 HARDWARE CONTEXT FEATURES BELONG IN MACHINE BACKENDS

LATER ITS USES KA/KL/KS-SPECIFIC USER/EXECUTIVE AC CONTEXT AND MAPPING
FACILITIES TO AVOID SOFTWARE COPYING WHICH THE PDP-6 MUST PERFORM EXPLICITLY.

DAIMOS SHOULD NOT WEAKEN THE PDP-6 BASELINE TO DEPEND ON THESE FEATURES, BUT
FUTURE KA10/KI10/KL10/KS10 PROC BACKENDS SHOULD USE AVAILABLE HARDWARE CONTEXT
SELECTION WHEN IT REMOVES SAVE/RESTORE CODE OR MEMORY TRAFFIC.  THIS IS A
MACHINE-SPECIFIC OPTIMIZATION, NOT A COMMON KCORE REPRESENTATION CHANGE.

### 13.8 SPLITTING ITS INTO CORE/IOELEV/DISK/ITSDEV DID NOT CREATE A BETTER
###      GENERIC DEVICE ABSTRACTION FOR DAIMOS

BY THE LATER SOURCE LINE, MUCH OF ITS'S MEMORY, DISK, I/O-ELEVATOR, AND DEVICE
CODE IS ASSEMBLED FROM SEPARATE SOURCE MODULES.  THE UNDERLYING COMPACT
REPRESENTATIONS REMAIN THE SAME: ONE-WORD IOBFT RECORDS, PACKED BYTE FIELDS,
DIRECT DEVICE-SPECIFIC SERVICE CODE, AND COMMON RESOURCE ALLOCATORS.

THERE IS NO LATE ITS EQUIVALENT OF A LARGE GENERAL DEVICE OBJECT WHICH DAIMOS
SHOULD COPY.  THE SPLIT IS SOURCE ORGANIZATION, NOT AN ARGUMENT FOR GROWING
DAIMOS RUNTIME ABSTRACTIONS.

## 14. TENEX-DERIVED SIZE-OPTIMIZATION CONCEPTS

TENEX 128/133/134/135 ADDS FEWER FUNDAMENTALLY NEW SIZE TECHNIQUES THAN JOSS,
MONITOR 1.4, OR ITS, BUT IT IS USEFUL BECAUSE IT SHOWS HOW THOSE PDP-10
TECHNIQUES SCALE IN A MUCH LARGER PAGED MONITOR.  THE IMPORTANT LESSONS ARE
THE RESIDENT/SWAPPABLE CODE BOUNDARY, CENTRALIZED LITERALS, PACKED
DATA+PREDICATE WAIT STATE, AND RELENTLESS HALFWORD PACKING OF POINTER/LIST
STATE.

### 14.1 CENTRALIZE COMMON ADDRESSABLE LITERALS WHEN THE ASSEMBLER DOES NOT
###      COALESCE THEM

TENEX TTYSRV EXPLICITLY STATES:

    DEFINE SOME HANDY CONSTANTS AS GLOBALS TO REDUCE DUPLICATED LITERALS

IT THEN REUSES WORDS WHICH ALREADY EXIST IN PERMANENT TABLES:

- ZERO ALIASES A 0,,0 WORD IN BHC.
- ONE ALIASES THE WORD IN BITS CONTAINING VALUE 1.
- TWO ALIASES THE WORD IN BITS CONTAINING VALUE 2.
- MINUS1 IS ONE SHARED WORD FOR -1.

THIS IS MORE AGGRESSIVE THAN MERELY CREATING A CONSTANT POOL: WHERE POSSIBLE,
THE CONSTANT NAME IS AN ALIAS OF AN ALREADY-REQUIRED PERMANENT TABLE WORD AND
THEREFORE COSTS ZERO ADDITIONAL RAM.

DAIMOS HANDWRITTEN ASSEMBLY CONTAINS MANY REPEATED ADDRESS LITERALS.  A SOURCE
CENSUS CURRENTLY FINDS, AMONG OTHERS:

- [1,,1]       DOZENS OF TIMES.
- [2,,2]
- [3,,3]
- [5,,5]
- [7,,7]
- REPEATED POINT 6/8/10 DESCRIPTORS.

FIRST VERIFY DAS/DLINK LITERAL-POOL BEHAVIOR.  IF IDENTICAL LITERALS ARE
ALREADY COALESCED ACROSS THE FINAL LINK, DO NOTHING.  IF THEY ARE ONLY
COALESCED PER OBJECT OR NOT AT ALL, TEST A SMALL SHARED KCORE LITERAL SET FOR
THE MOST COMMON VALUES.

PREFER, IN ORDER:

1. ALIASING A REQUIRED EXISTING CONSTANT TABLE WORD.
2. ONE SHARED KCORE CONSTANT USED ACROSS MANY OBJECTS.
3. KEEPING THE LOCAL LITERAL WHEN IT OCCURS TOO FEW TIMES TO PAY FOR A GLOBAL.

DO NOT CREATE OBSCURE CROSS-SUBSYSTEM ALIASES SOLELY TO SAVE ONE WORD.  THE
ALIAS MUST BE A TRUE IMMUTABLE CONSTANT FOR THE ENTIRE BOOT.

EXPECTED VALUE: UNKNOWN UNTIL ASSEMBLER/LINKER LITERAL COALESCING IS MEASURED;
POTENTIALLY A CHEAP MULTIWORD KCORE WIN.

### 14.2 RESIDENT VS SWAPPABLE MONITOR CODE IS A CONCRETE OVERLAY MODEL

TENEX SPLITS MONITOR CODE EXPLICITLY BETWEEN RESPC AND SWAPPC.  INTERRUPT
ENTRY, SMALL RESOURCE TESTS, SCHEDULER-CRITICAL PRIMITIVES, AND MINIMAL
RESIDENT DISPATCH REMAIN IN CORE; LARGE USER-FACING FILE/DEVICE/CONTROL BODIES
CAN LIVE IN PAGED/SWAPPABLE MONITOR SPACE.

DAIMOS CANNOT COPY TENEX MONITOR PAGING ON THE PDP-6, BUT THE SAME SIZE
BOUNDARY CAN GUIDE A FUTURE EXPLICIT OVERLAY FACILITY:

    PERMANENT KCORE/MRES:
        TINY ENTRY/TRAMPOLINE
        PI-SAFE COMPLETION STATE
        SCHEDULER/LOCK/RESOURCE TEST

    COLD OVERLAY:
        FORMAT/CONTROL OPERATIONS
        RARE ADMINISTRATION
        LARGE VALIDATION/REPORTING PATHS
        OTHER CODE WHICH MAY BLOCK ONLY THROUGH A WELL-DEFINED RESIDENT ABI

ON A PDP-6, SUCH AN OVERLAY WOULD NEED A FIXED OVERLAY ADDRESS OR RELOCATION
AT LOAD TIME, A SINGLE SERIALIZED EXECUTION SLOT, AND A RESIDENT TRAMPOLINE.
THIS IS NOT A 0.9 OPTIMIZATION AND SHOULD NOT DELAY THE CURRENT SOURCE-LEVEL
SHRINK.

THE IMPORTANT TENEX LESSON IS THAT THE OVERLAY BOUNDARY SHOULD BE AT WHOLE
COLD OPERATIONS, NOT ARBITRARY FRAGMENTS OF HOT DEVICE/SCHEDULER CODE.

CURRENT ASSESSMENT: POST-0.9 OPTION FOR REDUCING PERMANENT RESIDENT TEXT WHEN
THE CHEAPER KCORE/MRES SHRINK IS EXHAUSTED.

### 14.3 KEEP TINY RESIDENT PREDICATES IN FRONT OF COLD/OVERLAY BODIES

TENEX SOMETIMES PLACES ONLY A SMALL TEST OR INITIALIZER IN RESPC WHILE THE
LARGER OPERATION LIVES IN SWAPPC.  FOR EXAMPLE, DUMP-I/O RESOURCE TESTING IS
RESIDENT WHILE THE BULK DUMP OPERATION IS SWAPPABLE.

THIS GIVES A USEFUL DAIMOS OVERLAY RULE:

    IF THE SCHEDULER/PI PATH NEEDS TO ASK "CAN THIS PROCEED?", KEEP THAT TEST
    RESIDENT EVEN IF THE OPERATION WHICH CONSUMES THE RESOURCE IS COLD.

THIS AVOIDS MAKING OVERLAY CODE PART OF INTERRUPT OR WAKEUP CRITICAL PATHS.

### 14.4 FKSTAT PACKS WAIT DATA AND THE PREDICATE ADDRESS INTO ONE WORD

TENEX'S PER-FORK FKSTAT WORD IS A DIRECT GENERALIZATION OF ITS'S EXECUTABLE
FLSINS IDEA.  EDISMS STORES:

    LH = DATA FOR THE WAIT TEST
    RH = RESIDENT TEST-ROUTINE ADDRESS

THE WAIT-LIST SCANNER DOES:

    MOVE 2,FKSTAT(FORK)
    HLRZ 1,2
    JSP 4,0(2)

THE TEST ROUTINE SKIPS WHEN THE FORK IS READY.  ONE WORD THEREFORE DESCRIBES
BOTH WHAT TO TEST AND HOW TO TEST IT, WITHOUT A WAIT-CLASS SWITCH TABLE.

DAIMOS'S CURRENT WAIT-CHANNEL DESIGN IS BETTER FOR 0.9 BECAUSE EVENTS WAKE
WAITERS DIRECTLY AND THE RUN QUEUE NEED NOT POLL EVERY BLOCKED PROCESS.
HOWEVER, IF DAIMOS LATER ADOPTS EXPLICIT RESTARTABLE BLOCKING TO SHRINK
U-AREAS, A ONE-WORD DATA+PREDICATE DESCRIPTOR IS A STRONG REPRESENTATION
CANDIDATE FOR COLD OR POLLED CONDITIONS.

DO NOT REPLACE EVENT-DRIVEN WAITS WITH PERIODIC SCANNING JUST TO COPY TENEX.

### 14.5 TENEX AGAIN VALIDATES BLT FOR CONTEXT AND PI AC SAVING

TENEX PI AND SCHEDULER CODE USES BLT EXTENSIVELY FOR AC BLOCK SAVE/RESTORE,
INCLUDING SMALL PI-LEVEL SAVE AREAS AND WHOLE USER/MONITOR AC BLOCKS.

THIS IS THE THIRD INDEPENDENT PDP-6/10 SYSTEM SUPPORTING THE SAME CONCLUSION:
DAIMOS PROC_SAVE_USER/PROC_SAVE_KERNEL/PROC_RESTORE_* SCALAR AC MOVES SHOULD
BE CONVERTED TO BLT WHERE LEGAL.

NO NEW ACTION BEYOND THE EXISTING HIGH-PRIORITY BLT ITEM IS REQUIRED.

### 14.6 TENEX PI DISPATCH FURTHER SUPPORTS STATIC/LINKED SERVICE PATHS

TENEX PI CHANNELS USE CONFIGURATION-TIME STRAIGHT-LINE SERVICE SEQUENCES.  A
CHANNEL SAVES ONLY THE REQUIRED ACS, THEN CALLS THE DEVICE SERVICE ROUTINES
WHICH CAN EXIST ON THAT CHANNEL, AND RESTORES ONCE at the common tail.

THIS IS NOT A GENERAL RUNTIME HANDLER LIST.  IT FURTHER SUPPORTS THE DAIMOS
PLAN TO REPLACE THE MULTI-HANDLER PI TABLE/SPAN ITERATOR WITH MINIT-LINKED
HANDLER CHAINS.

TENEX ALSO SHOWS A POSSIBLE SECOND-PASS OPTIMIZATION AFTER LINKED CHAINS:
SAME-LEVEL HANDLERS MAY SHARE ONE SAVE/RESTORE ENVELOPE WHEN THEIR AC-CLOBBER
CONTRACTS ARE COMPATIBLE.  DAIMOS ALREADY SAVES AT THE LEVEL ENTRY, SO THE
PRIMARY WIN REMAINS REMOVING THE TABLE/SPAN INTERPRETER rather than changing
individual handlers.

### 14.7 PACKED LIST LINKS CONFIRM THE CURRENT DAIMOS PROCESS-DESCRIPTOR STYLE

TENEX FKPT STORES PREVIOUS AND NEXT RUN/WAIT LIST LINKS IN THE TWO 18-BIT
HALVES OF ONE WORD.  FKQ STORES QUEUE NUMBER AND REMAINING QUANTUM TOGETHER;
FKJOB STORES JOB NUMBER AND JOB-STORAGE POINTER TOGETHER.

DAIMOS ALREADY GOES FURTHER for its smaller process model by reusing SCHED RH
according to process state and packing multiple scheduler attributes in LH.
THERE IS NO TENEX-DERIVED REASON TO GROW THE THREE-WORD PROC DESCRIPTOR.

### 14.8 ONE SCAN SHOULD RETURN SIZE/FRAGMENTATION INFORMATION

TENEX ASGFRE KEEPS A TOTAL FREE-SPACE COUNT IN THE FREE-STORAGE HEADER, AND
ITS BEST-FIT PASS ALSO REMEMBERS THE LARGEST BLOCK SEEN.  A FAILED ALLOCATION
THEREFORE HAS USEFUL INFORMATION WITHOUT ANOTHER COMPLETE PASS.

DAIMOS SHOULD NOT ADD TENEX'S HEADER OR BEST-FIT POLICY, BUT THIS IS ANOTHER
INDEPENDENT VALIDATION OF THE ALREADY-IDENTIFIED MM CHANGE: THE FAILED
MM_FIND_FIT PASS SHOULD RETURN ENOUGH INFORMATION TO DISTINGUISH FRAGMENTED
FROM NOMEM WITHOUT MM_TOTAL_FREE() RESCANNING THE EXTENTS.

### 14.9 POST-LINK SYMBOL/PROGRAM COMPACTION HAS NO CURRENT DAIMOS RESIDENT
###      EQUIVALENT TO REMOVE

TENEX POSTLD REMOVES LOCAL/GENERATED/DUPLICATE SYMBOLS, COMPACTS THE SYMBOL
TABLE IN PLACE, AND CAN DROP OPTIONAL PROGRAM BLOCKS TO MAKE THE FINAL MONITOR
IMAGE FIT.

THE ANALOGOUS DAIMOS AUDIT CHECKED THE DEFERRED MOVABLE-MODULE SUPPORT.
MODULE_RUNTIME.C DEFINES DESCRIPTORS/BINDING TABLES FOR FUTURE MODULE MOVES,
BUT MODULE_RUNTIME.S IS NOT PART OF THE CURRENT KCORE_FIXED_ASM LINK LIST.
THOSE DEFERRED TABLES THEREFORE COST NO PRESENT RESIDENT WORDS.

KEEP THIS PROPERTY: DEVELOPMENT OR FUTURE RELOCATION METADATA MUST NOT ENTER
THE 0.9 RESIDENT IMAGE UNTIL THE FEATURE ACTUALLY NEEDS IT.

### 14.10 TENEX GENERAL DEVICE TABLES SHOULD NOT REPLACE DAIMOS MRES VECTORS

TENEX HAS A RICH PER-DEVICE MODEL:

- DEVNAM
- DEVCHR
- DEVDSP
- DEVUNT
- A LARGE FIXED POSITIONAL SERVICE VECTOR FOR EACH DEVICE

UNSUPPORTED OPERATIONS POINT AT COMMON STUBS SUCH AS CPOPJ, WHICH IS COMPACT
FOR TENEX'S LARGE COMMON FILE/DEVICE ABI.  DAIMOS'S SMALLER WORD-STREAM
PROVIDERS AND HALFWORD-PACKED MRES VECTORS ARE ALREADY MORE COMPACT FOR ITS
REQUIREMENTS.

THE ONLY TRANSFERABLE RULE IS TO USE GLOBAL COMMON STUBS FOR UNSUPPORTED OR
TRIVIAL OPERATIONS RATHER THAN PRIVATE PER-MODULE RETURNS.  DAIMOS ALREADY
USES KRET_ZERO/KRET_NEG* AND ZERO VECTOR ENTRIES extensively.  INCLUDE SUCH
STUBS IN THE FINAL CROSS-DOMAIN P10FOLD CENSUS, BUT DO NOT ADD A TENEX DDB
LAYER.

### 14.11 POST-LOAD COMPACTION SUGGESTS A FINAL IMAGE-ONLY DEAD-DATA AUDIT

TENEX'S POSTLD THINKS IN TERMS OF THE FINAL LOADED IMAGE, NOT ONLY SOURCE
FILES.  THE DAIMOS FINAL SHRINK SHOULD DO THE SAME AFTER ALL SOURCE CHANGES:

- IDENTIFY UNREFERENCED KCORE/MRES DATA WORDS WHICH SURVIVE ASSEMBLY/LINK.
- CHECK DUPLICATED LITERAL/POINT WORDS ACROSS OBJECT BOUNDARIES.
- CHECK ZERO/ONE/COMMON MASK WORDS WHICH CAN ALIAS EXISTING IMMUTABLE DATA.
- CHECK OPTIONAL TABLE HOLES WHICH ARE STILL MATERIALIZED IN THE FINAL IMAGE.
- CHECK BUILD RULES FOR OBJECTS GENERATED BUT NOT ACTUALLY LINKED, TO AVOID
  CONFUSING SOURCE SIZE WITH RESIDENT SIZE.

THIS FINAL IMAGE AUDIT SHOULD FOLLOW P10SUPER/P10FOLD AND USE LINKED ADDRESSES
AS THE AUTHORITY.
