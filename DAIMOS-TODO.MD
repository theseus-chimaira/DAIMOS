# DAIMOS VERSION 0.9 ROADMAP

THIS FILE DEFINES OPEN WORK REQUIRED TO REACH VERSION 0.9.  THE PREVIOUS
PRE-USERLAND ACCEPTANCE REMAINS THE BASELINE, BUT THE PDP-6/JOSS OPTIMIZATION
HANDOFF AND A REAL INIT ARE NOW EXPLICIT PRE-DSH GATES.

DO NOT BEGIN THE DSH IMPLEMENTATION PHASE UNTIL SECTIONS 1 THROUGH 7 BELOW
HAVE PASSED THEIR ACCEPTANCE TESTS.

## 1. PRE-DSH SCHEDULER CENSUS AND INVARIANTS

THE CURRENT SCHEDULER HAS ALREADY BEEN REDUCED FROM TWO PROCESS-TABLE PASSES
PER TICK TO ONE, BUT AN ORDINARY CLOCK TICK STILL SCALES WITH THE ACTIVE
PROCESS TABLE.  COMPLETE THE PDP-6/JOSS SCHEDULER WORK BEFORE DSH.

ADD TEMPORARY TEST/DEBUG INSTRUMENTATION FOR:

- TOTAL SCHEDULER TICKS.
- FAST-PATH TICKS.
- FULL RUNNABLE SELECTIONS.
- PROCESS SLOTS INSPECTED.
- RUN-QUEUE WALKS.
- RUN-QUEUE INSERTIONS AND REMOVALS.
- FORCED RESCHEDULES.

MEASURE AT LEAST:

- ONE RUNNABLE PROCESS.
- TWO CPU-BOUND PROCESSES.
- 16 RUNNABLE PROCESSES.
- A HIGH/FULL CONFIGURED PROCESS TABLE.
- NICE EXTREMES.
- SLEEP/WAKEUP LOAD.
- STOP/CONT AND JOB-CONTROL TRANSITIONS.
- PROCESS EXIT, REAP, AND SLOT REUSE.
- MAXIMUM KERNEL-STACK DEPTH THROUGH SCHEDULER PATHS.

THE COUNTERS ARE MEASUREMENT TOOLS.  DO NOT KEEP THEM AS PERMANENT RESIDENT
STATE UNLESS A LATER USE JUSTIFIES THEIR COST.

## 2. INTRUSIVE RUNNABLE QUEUE

IMPLEMENT A RUNNABLE QUEUE WITHOUT ENLARGING THE THREE-WORD PROCESS
DESCRIPTOR.

REUSE THE EXISTING SCHED WORD RH ACCORDING TO PROCESS STATE:

- PROC_SRUN: NEXT RUNNABLE PROCESS SLOT.
- PROC_SLEEP: WAIT CHANNEL.
- OTHER STATES: EXPLICITLY DOCUMENT THEIR STATE-SPECIFIC RH MEANING.

PREFER ONE RUN-QUEUE HEAD AND TAIL.  REUSE OR ELIMINATE EXISTING GLOBAL
SCHEDULER STATE IF THAT MAKES THE GLOBAL COST ZERO OR ONE WORD.

INITIAL IMPLEMENTATION MUST PRESERVE THE CURRENT NICE/RECENT-CPU POLICY.
DO NOT CHANGE TO PURE FIFO MERELY TO MAKE THE QUEUE SMALLER.

REQUIRED INVARIANTS AND TESTS:

- EVERY RUNNABLE PROCESS APPEARS EXACTLY ONCE.
- EVERY NON-RUNNABLE PROCESS APPEARS ZERO TIMES.
- QUEUE TRAVERSAL TERMINATES.
- EVERY QUEUED SLOT IS VALID AND ACTIVE.
- EMPTY AND ONE-ELEMENT HEAD/TAIL STATES ARE CONSISTENT.
- SLEEP, WAKEUP, STOP, CONTINUE, EXIT, REAP, RUN, AND SLOT REUSE KEEP
  THE QUEUE CONSISTENT.
- NICE BEHAVIOR REMAINS ACCEPTABLE.
- SELECTION EXAMINES RUNNABLE PROCESSES, NOT UNUSED OR SLEEPING TABLE SLOTS.

DO NOT ADD A JOSS-STYLE EXTRA QUEUE-LINK WORD PER PROCESS.

## 3. QUANTUM FAST PATH AND COARSE SCHEDULER ACCOUNTING

AFTER THE RUN QUEUE IS PROVEN CORRECT, MAKE THE ORDINARY TIMER TICK
EFFECTIVELY O(1).

THE NORMAL PATH SHOULD:

- ACCOUNT THE CURRENT PROCESS.
- DECREMENT ITS QUANTUM.
- RETURN TO IT IMMEDIATELY WHEN NO RESCHEDULE CONDITION EXISTS AND THE
  QUANTUM REMAINS.

FULL SELECTION IS REQUIRED FOR AT LEAST:

- QUANTUM EXPIRATION.
- BLOCK/SLEEP.
- EXIT.
- STOP.
- EXPLICIT YIELD/RESCHEDULE.
- POLICY-RELEVANT HIGHER-PRIORITY WAKEUP.
- JOB-CONTROL OR EVENT TRANSITIONS WHICH MAKE THE CURRENT PROCESS UNRUNNABLE.

MOVE WHOLE-SYSTEM RECENT-CPU DECAY, SLEEP AGING, AND PRIORITY MAINTENANCE TO
A COARSER EXISTING CLOCK BOUNDARY OR STATE TRANSITIONS.  DO NOT TOUCH EVERY
PROCESS ON EVERY TICK MERELY TO AGE IT.

PRESERVE OBSERVABLE FAIRNESS AND NICE BEHAVIOR.  IF KCC OUTPUT FOR THE HOT
PATH REMAINS SUBSTANTIALLY LARGER OR SLOWER, COMPARE A SMALL PDP-10 ASSEMBLY
HOT PATH AGAINST THE C VERSION.  KEEP ASSEMBLY ONLY FOR A MEASURED RAM OR
EXECUTION WIN.

ACCEPTANCE REQUIRES:

- NO NEW PER-PROCESS WORD.
- ORDINARY TICK COST EFFECTIVELY CONSTANT-TIME.
- NON-RUNNABLE TABLE SLOTS NOT SCANNED FOR NORMAL SELECTION.
- JOB CONTROL, SLEEP/WAKEUP, SWAP, WAIT, PIPE, AND SLOT-REUSE REGRESSIONS PASS.
- KERNEL-STACK USE DOES NOT MATERIALLY INCREASE.
- ANY RESIDENT GROWTH IS EXPLICITLY JUSTIFIED BY A MEASURED EXECUTION WIN.

THIS IS NOT A ZERO-GROWTH RULE.  A FEW RESIDENT WORDS ARE ACCEPTABLE WHEN
THEY BUY A LARGE MEASURED COMMON-PATH EXECUTION WIN; RAM AND EXECUTION COST
MUST BE EVALUATED TOGETHER.

## 4. MEMORY-MANAGER DESCRIPTOR CENSUS

BEFORE CHANGING THE MM REPRESENTATION, ADD TEMPORARY MEASUREMENT FOR:

- MAXIMUM SIMULTANEOUS ALLOCATED EXTENTS.
- MAXIMUM TOTAL EXTENTS.
- MAXIMUM FREE EXTENTS.
- MAXIMUM FRAGMENTATION LEVEL.
- NUMBER OF MANAGED ARENAS/RANGES.
- ALLOCATIONS BY TYPE.
- COMPACTIONS AND WORDS MOVED.
- DESCRIPTOR-EXHAUSTION FAILURES.
- CONTIGUOUS-SPACE FAILURES.

RUN THE COMPLETE MM, COMPACTION, SWAP, FILESYSTEM, DRIVER, AND LOW-MEMORY
REGRESSION SET.  REMOVE THE TEMPORARY COUNTERS AFTER THE DECISION UNLESS THEY
PROVE WORTH THEIR PERMANENT COST.

## 5. ALLOCATED-EXTENTS-ONLY MM EXPERIMENT

USING THE CENSUS FROM SECTION 4, PROTOTYPE THE HANDOFF'S ALTERNATIVE MM
REPRESENTATION:

- STORE ONLY ALLOCATED EXTENTS, SORTED BY ADDRESS.
- REPRESENT FREE SPACE AS IMPLICIT GAPS BETWEEN ALLOCATIONS AND ARENA
  BOUNDARIES.
- ALLOCATION INSERTS ONE ALLOCATED DESCRIPTOR.
- FREE REMOVES ONE DESCRIPTOR.
- REMOVE FREE-EXTENT SPLIT/COALESCE BOOKKEEPING WHERE IT BECOMES UNNECESSARY.

COMPARE AGAINST THE CURRENT EXPLICIT FREE/USED EXTENT TABLE FOR:

- PERMANENT DESCRIPTOR RAM.
- KCORE SIZE.
- ALLOCATION/FREE EXECUTION COST.
- FRAGMENTATION.
- COMPACTION CORRECTNESS.
- DESCRIPTOR AND CONTIGUOUS-SPACE FAILURE BEHAVIOR.

KEEP THE NEW REPRESENTATION ONLY IF IT IS CLEARLY BETTER OVERALL.  DO NOT
ADOPT 1K-WORD ALLOCATION GRANULARITY.

ALSO INVESTIGATE WHETHER MOVABLE PROCESS MEMORY CAN USE SIMPLER BOOKKEEPING
THAN THE GENERAL MM.  DO NOT ADD A SECOND ALLOCATOR UNLESS IT REDUCES BOTH
PERMANENT BOOKKEEPING AND OVERALL CODE/EXECUTION COMPLEXITY.

## 6. SWAP AND COMPACTION PLANNING

MEASURE THE CURRENT NUMBER OF:

- SWAP VICTIMS SELECTED.
- SWAP-OUT AND SWAP-IN OPERATIONS.
- ALLOCATION RETRY CYCLES.
- COMPACTIONS BEFORE AND AFTER SWAP.

IF REAL TESTS SHOW REPEATED AVOIDABLE SWAP/COMPACT/RETRY CYCLES, IMPLEMENT A
PLANNED RECLAIM PASS:

1. DETERMINE THE REQUIRED CONTIGUOUS SIZE AND ALIGNMENT.
2. DETERMINE WHETHER COMPACTION ALONE CAN SATISFY IT.
3. IF NOT, SELECT ENOUGH VICTIMS TO MAKE THE REQUIRED GAP POSSIBLE.
4. SWAP THOSE VICTIMS OUT.
5. COMPACT ONCE.
6. RETRY THE ALLOCATION ONCE.

VICTIM POLICY SHOULD CONTINUE TO CONSIDER RUNNABLE/SLEEPING STATE,
RECENT CPU ACTIVITY, NICE/PRIORITY, RECLAIM SIZE, AND SWAP I/O COST.
DO NOT KEEP A MORE COMPLEX POLICY IF THE MEASUREMENTS SHOW NO REAL GAIN.

## 7. REAL INIT BEFORE DSH

IMPLEMENT A REAL, SEPARATE USERLAND `/SYSTEM/INIT` BEFORE DSH DEVELOPMENT
CONTINUES.  THE CURRENT BOOT MAKEFILE INSTALLS `$(DSH_DXR)` AS `/SYSTEM/INIT`;
THAT TEMPORARY ALIAS MUST BE REMOVED.

THE VERSION 0.9 INIT SHOULD BE SMALL AND PURPOSEFUL:

- BUILD A DISTINCT INIT EXECUTABLE AND INSTALL IT AS `/SYSTEM/INIT`.
- KEEP INIT AS THE FIRST USER PROCESS/PID 1 AND THE ORPHAN REAPER.
- ESTABLISH THE INITIAL SESSION, DOMAIN, PROCESS GROUP, FOREGROUND TTY, AND
  CTY DESCRIPTOR STATE EXPLICITLY.
- LAUNCH `/SYSTEM/DSH` AS A CHILD WITH STDIN/STDOUT/STDERR MAPPED TO CTY.
- REAP ALL CHILDREN AND ADOPTED ORPHANS SO ZOMBIES CANNOT ACCUMULATE.
- WHEN THE PRIMARY CONSOLE DSH EXITS, REAP IT AND RESPAWN A FRESH CONSOLE DSH.
- KEEP INIT INDEPENDENT OF DSH BUILTINS AND COMMAND-PARSER INTERNALS.
- DO NOT ADD A GENERAL SERVICE MANAGER, RC LANGUAGE, OR CONFIGURATION SYSTEM
  FOR VERSION 0.9 UNLESS A CONCRETE BOOT REQUIREMENT APPEARS.

TEST AT LEAST:

- `/SYSTEM/INIT` AND `/SYSTEM/DSH` ARE DISTINCT IMAGES.
- BOOT ENTERS INIT AS THE FIRST USER PROCESS.
- INIT LAUNCHES DSH WITH THE EXPECTED SESSION/PGRP/TTY STATE.
- DSH EXIT IS REAPED AND DSH IS RESPAWNED.
- ORPHANED CHILDREN ARE ADOPTED AND REAPED BY INIT.
- REPEATED SHELL EXIT/RESPAWN DOES NOT LEAK PROCESS SLOTS, FILE DESCRIPTORS,
  U-AREAS, OR SWAP BACKING.
- STOP/CONT/JOB-CONTROL OPERATIONS ON DSH DO NOT STOP INIT.

ONLY AFTER SECTIONS 1 THROUGH 7 PASS IS DSH THE NEXT IMPLEMENTATION PHASE.

## 8. PRESERVE THE KERNEL ABI FOUNDATION

- KEEP KCC AND GCC CALLING CONVENTIONS ABI COMPATIBLE.
- KEEP EXECUTIVE INTERNAL SERVICE CALLS ON DIRECT REGISTER BRIDGES UNLESS
  MEASUREMENT PROVES A DIFFERENT ABI SMALLER AFTER TRAP COST IS INCLUDED.
- KEEP COMMON VFS, MRES, DEVICE, AND SERVICE DISPATCH PATHS SHARED.
- FIX ASSEMBLER OR COMPILER DEFECTS AT THEIR SOURCE BEFORE LOWER-PRIORITY WORK.

## 9. COMPLETE DSH FOR DAILY USE

- USE THE EXISTING DAIMOSV1 DSH IMPLEMENTATION AS THE STARTING POINT.
- COMPLETE PIPELINE EXECUTION, REDIRECTION, PROCESS GROUPS, FOREGROUND AND
  BACKGROUND CONTROL, AND BUILTINS REQUIRED FOR BOOTSTRAP/ADMINISTRATION.
- INTEGRATE THE GETOPT HELP/MANUAL-PAGE MODEL AND THE DEFERRED STRUCTURED
  COMPLETION INTERFACE WITHOUT DUPLICATING COMMAND METADATA.
- KEEP PARSING SMALL AND PURPOSEFUL.

## 10. PORT MAKE AND ITS DEPENDENCIES

- PORT THE MINIMUM MAKE IMPLEMENTATION AND SUPPORT UTILITIES REQUIRED FOR
  NATIVE BUILDS.
- REMOVE HOST-ONLY ASSUMPTIONS FROM THE DAIMOS BUILD PATH.
- VERIFY A NATIVE EDIT/BUILD/INSTALL CYCLE BEFORE EXPANDING FEATURES.

## 11. PORT DAS

- BUILD DAS NATIVELY AFTER THE MINIMUM MAKE ENVIRONMENT WORKS.
- VERIFY ASSEMBLY AND LINKING OF REPRESENTATIVE USER AND SYSTEM OBJECTS.
- FIX DAS OR LINKER DEFECTS PROPERLY; DO NOT ADD DAIMOS-SPECIFIC WORKAROUNDS.

## 12. PORT ELVIS AND THE PRACTICAL USER TOOLSET

- COMPLETE THE FEATURE-RICH ELVIS VI/EX PORT WITH SPELLING AND FOLDING.
- KEEP SYNTAX HIGHLIGHTING, COLORS, URL FEATURES, AND NON-SIXBIT RECORD
  FEATURES OUT OF THE PORT.
- PROVIDE THE BASIC FILE, DIRECTORY, TEXT, COPY, MOVE, REMOVE, AND SYSTEM
  INSPECTION UTILITIES REQUIRED FOR DAILY USE AND SELF HOSTING.

## 13. PREPARE AND PORT KCC

- VERIFY KCC/GCC ABI INTEROPERABILITY WITH MIXED OBJECTS.
- SWITCH THE MAIN DAIMOS COMPILER TO KCC TEMPORARILY WHEN THE NATIVE TOOL PATH
  IS READY, SO ABI AND CODE-GENERATION DEFECTS ARE FOUND EARLY.
- PORT THE REQUIRED KCC FRONT END, BACK END, LIBRARY SUPPORT, AND BUILD RULES.
- BUILD KCC UNDER DAIMOS AND VERIFY ITS OUTPUT WITH DAS AND GCC OBJECTS.

## 14. REVISIT USERSPACE OVERLAYS AFTER MEASUREMENT

USERSPACE OVERLAYS ARE NOT A PRE-DSH OR INITIAL SELF-HOSTING GATE.  MEASURE
NATIVE DAS AND ELVIS FIRST.  ONLY THEN DECIDE WHETHER AN OVERLAY ABI IS
JUSTIFIED.  FOLLOW PDP10-DOC KERNEL/MEMORY-MANAGEMENT.MD AND
KERNEL/SELFHOSTING.MD.

## 15. ADD THE RUNTIME MODULE LOADER

THIS REMAINS AFTER THE INITIAL USER ENVIRONMENT AND SELF-HOSTING PORT.

- LOAD MOVABLE MODULES INTO MANAGED CORE.
- APPLY RELOCATION AND SERVICE BINDINGS.
- COMPACT MOVABLE MODULES WITH THE MEMORY MANAGER.
- LOAD SLOW DEVICE SUPPORT ON DEMAND WHERE APPROPRIATE.
- AUTO-UNLOAD AUTOMATICALLY LOADED MODULES AFTER THEIR LAST HANDLE IS RELEASED.
- KEEP MANUALLY LOADED MODULES RESIDENT UNTIL EXPLICITLY UNLOADED.
- VERIFY FAILURE AT EVERY LOAD, RELOCATION, BIND, MOVE, AND UNLOAD BOUNDARY.

## 16. VERSION 0.9 VALIDATION

- RUN MULTIUSER SCHEDULER, PIPE, FILE-DESCRIPTOR, COMPACTION, AND SWAP STRESS.
- RUN D6FS AND DTFS MUTATION, RECOVERY, MEDIA-FULL, AND STORAGE-ERROR TESTS.
- RUN MODULE MOVE/UNLOAD STRESS AFTER THE LOADER EXISTS.
- MEASURE INTERACTIVE LATENCY ON PDP-6 CLASS HARDWARE OR SIMULATION.
- KEEP KCORE PLUS NORMAL FULL-BOOT MRES WITHIN THE DOCUMENTED RESIDENT LIMIT OR
  EXPLICITLY REVISE THAT LIMIT BEFORE ACCEPTING REQUIRED KERNEL FUNCTIONALITY.
- REQUIRE CLEAN DAIMOS, DAIMOS-TESTKIT, DAS, KCC, AND PDP10-TOOLS REGRESSIONS.
- REQUIRE NO KNOWN COMPILER OR ASSEMBLER BUG AFFECTING GENERATED SYSTEM CODE.

## 17. NOT PART OF VERSION 0.9

NETWORKING IS COMPLETELY DEFERRED.  DO NOT IMPLEMENT OR PORT A NETWORK STACK,
NETWORK PROTOCOLS, NETWORK USER UTILITIES, OR NETWORK-DEPENDENT SERVICES AS A
VERSION 0.9 REQUIREMENT.

SOCKETS ARE NOT CURRENTLY A VERSION 0.9 REQUIREMENT EITHER.  THEIR API,
SEMANTICS, RELATIONSHIP TO FILE DESCRIPTORS, AND TARGET VERSION MUST BE
DISCUSSED SEPARATELY BEFORE ANY SOCKET ABI IS ADDED.

THE COMPACT TIMER/EVENT MODEL FROM THE PDP-6/JOSS HANDOFF REMAINS A DESIGN
REFERENCE FOR A FUTURE FEATURE WHICH ACTUALLY NEEDS GENERAL TIMERS.  DO NOT
ADD A GENERAL TIMER SUBSYSTEM NOW MERELY IN ANTICIPATION OF NETWORKING.
