## 4. D6FS SWAP AND LOGSTORE RESERVATIONS

EACH D6FS FILESYSTEM MAY CONTAIN ZERO OR ONE SWAP RESERVATION AND ZERO OR ONE
LOGSTORE RESERVATION.  THEY ARE NOT FILES AND HAVE NO ORDINARY FILE I/O OR
NAMESPACE SEMANTICS.  D6FS OWNS THEIR PERSISTENT LOGICAL RESERVATIONS AND
EXCLUDES THE BLOCKS FROM NORMAL ALLOCATION.

VFS DISCOVERS AND REGISTERS THE RESOLVED BACKING LOGICAL RANGE.  ONCE ACTIVE,
SWAP/LOGSTORE I/O BYPASSES FILE I/O AND USES THE LOWER BLOCK/BLOCKSET FAST PATH.
THE STORAGE-SET LAYER ALONE CHOOSES PHYSICAL DISTRIBUTION AND BAD-MEDIA
MAPPING; DEVICE DRIVERS OWN DEVICE-SPECIFIC SCHEDULING.  LOGICAL RESERVATIONS
ARE CONTIGUOUS EVEN WHEN THEIR PHYSICAL STORAGE IS DISTRIBUTED OR REMAPPED
AROUND BAD MEDIA.

ON SPINNING DISKS, SWAP IS PREFERRED AT THE FAST OUTER EDGE AND LOGSTORE AT THE
INNER EDGE DIRECTLY AFTER THE BOOT AREA.  SIZES AND BOUNDARIES ARE ALIGNED TO
DEVICE-PERFORMANCE GEOMETRY, NOT TO A RAM-SIZE MULTIPLIER.  DRUM MEDIA HAVE NO
INNER/OUTER RULE.  RESERVATIONS MAY BE CREATED, GROWN, SHRUNK, MOVED, OR
DELETED OFFLINE; MOVEMENT PRESERVES CONTENTS.  PACKFS PROVIDES FREE-RUN
PREPARATION.  MKFS.D6FS ACCEPTS INITIAL SWAP/LOGSTORE SIZES.  FSCK VALIDATES
AND REPAIRS THE RESERVATION/ALLOCATION RELATIONSHIP.  A FILESYSTEM PROVIDING
ACTIVE SWAP OR LOGSTORE CANNOT BE UNMOUNTED.

STATE: PARTIAL MIGRATION IMPLEMENTED THROUGH 2026-09-21.  BLOCKSET NO LONGER
OWNS LOGSTORE SEMANTICS: NEW D6FS V2 SUPERBLOCKS PERSIST THE LOGSTORE LOGICAL
START/LENGTH, KINIT VALIDATES THE SELECTED SUPERBLOCK RESERVATION, AND LOGSTORE
USES GENERIC LOWER-BLOCK I/O.  NEW D6FS V2 SUPERBLOCKS ALSO PERSIST THE ACTIVE
SWAP LOGICAL START/LENGTH.  FOR THE CURRENT DSK LAYOUT THE SWAP RANGE STARTS AT
D6FS TOTAL_BLOCKS AND EXTENDS INTO THE RAW TRAILING CAPACITY; DBOOT STILL
DESCRIBES THAT PHYSICAL CAPACITY BUT IS NO LONGER THE SEMANTIC OWNER ON NEW
MEDIA.  ALL-ZERO LEGACY V2 SWAP RESERVATION WORDS WITH A NONZERO DBOOT TAIL
MUST BE UPGRADED OFFLINE WITH `D6SWAP --MIGRATE-RESERVATION`; THE KERNEL NO
LONGER FALLS BACK TO THE LEGACY TAIL.  THE FIXED PDP-6 SWAP FAST PATH CACHES
THE SELECTED LOGICAL START/LENGTH AND DOES NOT REENTER D6FS FOR ACTIVE I/O.
GENERIC VFS RESERVATION OWNERSHIP IS NOW IMPLEMENTED WITH TYPED PER-MOUNT
SWAP AND LOGSTORE BITS PACKED INTO THE EXISTING MOUNT-FLAG WORD.  VFS PERMITS
ONLY ONE OWNER OF EACH RESERVATION TYPE SYSTEM-WIDE, REJECTS UNMOUNT BEFORE
SYNC OR PROVIDER TEARDOWN WHILE EITHER TYPE IS OWNED, AND CAN RELEASE SWAP OR
LOGSTORE INDEPENDENTLY WITHOUT DROPPING THE OTHER PIN.  ROOT D6FS ACTIVATION
PASSES THE SELECTED RESERVATION TYPES AT MOUNT CREATION; CALLERS MAY NOT CREATE
AN UNTYPED STORAGE PIN.  FILESYSTEM-INDEPENDENT LOGICAL STORAGE BACKING IS
NOW IMPLEMENTED AS A THREE-WORD DESCRIPTOR: PACKED READ/WRITE CALLBACKS, AN
EXPLICIT BACKING-SPECIFIC OPAQUE WORD, AND LOGICAL CAPACITY.  D6FS READERS
EMBED THAT DESCRIPTOR AND ALL FILE BLOCK I/O DISPATCHES THROUGH IT; DIRECT
UNIT/BASE AND CURRENT ROOT-BLOCKSET BRIDGES NOW LIVE IN THE STORAGE LAYER.
THE FIXED D6FS READER SINGLETON IS REMOVED.  EACH MOUNT OWNS A 17-WORD
MANAGED-CORE READER; THE TWO EXTRA WORDS KEEP THE FILESYSTEM UUID DISTINCT FROM
THE PHYSICAL A/B SUPERBLOCK LOCATIONS.  FIXED KCORE HOLDS ONE ACTIVE-READER
POINTER AND A FOUR-WORD O(1) MOUNT-ID SLOT VECTOR, BUT NO FIXED READERS.
PROVIDER DISPATCH SELECTS THE READER BY VNODE MOUNT ID.  THE RUNTIME
`SYS_EXT_D6FS_MOUNT` PATH CAN INSTALL AN INDEPENDENT READ-ONLY DIRECT-DSK D6FS
INSTANCE from a transiently validated handoff; TSFS and D6FS share the generic
serialized MOUNT_UNIT syscall bridge.  PDP-6 target regressions execute the
production selector, secondary-mount path, and cache lookup and prove distinct
reader, UUID/superblock, backing, mount-slot, and cache identities.  FULL
TWO-MEDIA SIMH ACCEPTANCE IS STILL BLOCKED BEFORE USERSPACE BY THE INDEPENDENT
`SLV FAIL` BOOT GATE, SO IT IS NOT CLAIMED AS PASSED.  PDP-6 TARGET REGRESSION
NOW EXECUTES THE PRODUCTION VFS MOUNT/RELEASE/UNMOUNT PATH AND PROVES TYPED
SWAP/LOGSTORE OWNERSHIP, CROSS-MOUNT EXCLUSIVITY, INDEPENDENT RELEASE, AND
UNMOUNT REJECTION WHILE A RESERVATION REMAINS ACTIVE.  D6FS FLUSH/CLEAN
UNMOUNT AND RO<->RW REMOUNT SEMANTICS ARE IMPLEMENTED.  THE V2 CRASH-RECOVERY
CONTRACT IS ALSO IMPLEMENTED: 36-BIT HALF-RANGE A/B SEQUENCE ORDERING, NO
FALLBACK FROM A NEWER DIRTY GENERATION TO AN OLDER CLEAN COPY, AND NO DIRTY
MOUNT EVEN READ-ONLY.  D6FSCK CHECK-ONLY MODE REPORTS DIRTY AS AN ERROR; -R
PERFORMS A FULL STRUCTURAL SCAN, WRITES ONLY DETERMINISTIC REPAIRS UNDER A
NEWER DIRTY GENERATION, THEN PUBLISHES CLEAN.  TARGET/HOST TESTS COVER TORN
DIRTY/CLEAN PUBLICATION, ORPHAN FCB RECLAMATION, LEAKED ALLOCATION REPAIR,
SUMMARY REBUILD, SEQUENCE WRAP, AND AMBIGUOUS-CORRUPTION NO-WRITE BEHAVIOR.
COMMON RUNTIME BAD-MEDIA MAPPING AND ARBITRARY SECONDARY-MOUNT SERVICE
ACTIVATION REMAIN OPEN.

## 9A. COMMON BAD-MEDIA REMAPPING

DISK AND DRUM STORAGE SETS USE THE SAME STABLE EXCEPTION-MAP MECHANISM.  A V1
PHYSICAL LOCATOR IS 18 BITS: TWO MEMBER BITS PLUS A 16-BIT MEMBER-LOCAL BLOCK
NUMBER.  THIS COVERS ALL FOUR CURRENT DSK270 UNITS (45056 SECTORS EACH) AND
ALL FOUR DRM236 UNITS (8192 BLOCKS EACH).  ONE 36-BIT WORD THEREFORE HOLDS ONE
SOURCE->REPLACEMENT REMAP.  KEEP THE TABLE SORTED AND SMALL; USE A LINEAR
SEARCH FOR THE PDP-6 PROFILE RATHER THAN A RESIDENT FULL-MEDIA BITMAP.

KNOWN DEFECTS SHOULD BE ASSIGNED STABLE SPARES WHEN A STORAGE-SET GENERATION IS
CREATED.  ADDING A REMAP MUST NEVER SHIFT EXISTING LOGICAL BLOCK NUMBERS.
DEVICE-SPECIFIC RETRY, ERROR DECODING, SEEK/ROTATION POLICY, AND RAW ADDRESS
FORMATION REMAIN IN DSK270/DRM236; ONLY THE EXCEPTION TRANSLATION AND PERSISTENT
MAP FORMAT ARE SHARED.  AN UNRECOVERABLE READ STILL REPORTS DATA LOSS; A
REPLACEMENT BLOCK CANNOT RECONSTRUCT CONTENT THAT COULD NOT BE READ.

STATE: DESIGN ACCEPTED, NOT IMPLEMENTED.  IMPLEMENT THE GENERIC STORAGE-SET
MAPPER BEFORE DUPLICATING ANY DISK-ONLY OR DRUM-ONLY BAD-BLOCK FACILITY.
